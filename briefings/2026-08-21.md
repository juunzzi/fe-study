# FE/AI 브리핑 — 2026-08-21

> 조사 창: 2026-08-19 ~ 08-21 (직전 회차는 [8/19](./2026-08-19.md), 8/20 회차는 없음)

## TL;DR

1. **8/26 에 Next.js critical 보안 패치가 예고됐다** — 패치 버전은 16.3.2 / 15.5.24. 우리는 16.3.0 이라 거의 확실히 영향권이다. CVE·영향 범위는 아직 비공개. ([공지](https://nextjs.org/blog/upcoming-nextjs-security-release-august-2026))
2. **Bun 1.4 가 나왔고, Rust 재작성이 실제로 출하됐다** — 8/13 회차 레이더에서 "예고"로 다뤘던 게 이번에 stable 이 됐다. Node 호환 테스트 1,517개 추가 통과, 유휴 CPU 1/5.
3. Vite 8.2.2 (8/20) · Vitest 4.1.11 (8/18) 은 저위험 패치. React 19.2.8 · TanStack Query 5.101.4 는 이미 최신. **TC39 는 8월 미팅 자체가 없다**(2026 미팅은 1·3·5·7·9월).
4. **`facebook/react` 가 `react/react` 로 리다이렉트된다** — React Foundation 이관 후속. 스크립트·문서에 org 를 하드코딩해 뒀으면 점검 대상.
5. 오늘의 학습 추천 — **MCP 2026-07-28 스펙의 stateless 전환**: initialize 핸드셰이크가 사라지고 각 요청이 자기 맥락을 들고 다닌다. juunzzi-bot 의 MCP 배선을 다시 볼 이유가 생겼다.

### ⚠️ Next.js — 8/26 critical 보안 릴리스 예고 (조치 필요)

[사전 공지](https://nextjs.org/blog/upcoming-nextjs-security-release-august-2026) (8/20). **2026-08-26 에 critical 등급 1건**을 패치하며, 패치 버전은 **16.3.2 / 15.5.24**. advisory 전문(영향 버전·공격 벡터·CVE)은 릴리스와 동시 공개라 지금은 알 수 없다.

**우리 영향**: 현재 **16.3.0**(8/3 릴리스). 8/26 에 16.3.2 로 올려야 한다. 지금 **16.3.1**(8/13)까지 미리 올려 두면 그날 diff 가 패치 하나로 줄어든다 — 16.3.0 → 16.3.1 은 패치 릴리스라 breaking 없음.

### Vite 8.2.1 → 8.2.2 (8/20)

[릴리스](https://github.com/vitejs/vite/releases/tag/v8.2.2). 패치, breaking 없음. 눈여겨볼 건 **`bundled-dev` 의 순환 import 를 full reload 대신 hot update 로 처리**(#23259) — 아래 "지금 알아둘 개념 ①" 이 정확히 이 이야기다. 그 외 sourcemap 경로를 sourcemap 위치 기준으로 해석(#23239), `resolve.preserveSymlinks` 를 root 해석에도 반영(#23198).

### Vitest 4.1.10 → 4.1.11 (8/18, 창 밖 하루)

[릴리스](https://github.com/vitest-dev/vitest/releases/tag/v4.1.11). 버그픽스 4건, breaking 없음. 그중 하나는 보안성이다 — `mocker` 의 redirect mock 을 fs allowlist 로 제한(#10974). **별도로 5.0.0-rc.2 가 8/17 에 나왔다** — 메이저가 임박했다는 신호이니 rc 릴리스 노트를 슬슬 봐 둘 시점.

### TypeScript — 새 릴리스 아님 (오해 주의)

8/20 에 `microsoft/TypeScript` 에 **v7.0.2 릴리스 엔트리가 생겼는데, 새 버전이 아니다.** 본문이 스스로 "This tag was originally released at: microsoft/typescript-go typescript/v7.0.2" 라고 밝힌다 — 실제 배포는 **2026-07-08**(npm 게시 시각도 동일)이고, 이번 건은 메인 레포로의 미러/백필이다. 릴리스 피드만 보고 "8월에 TS 가 나왔다"고 읽으면 틀린다.

**우리 영향**: 현재 **6.0.3**. stable 은 [7.0.2](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) — **메이저 하나 뒤처져 있다.** 7.x 는 Go 네이티브 포팅(컴파일 ~10배)이라 이득이 큰 대신 메이저 이행이므로, 8/19 회차에서 그린 lint 스택 peer 제약과 함께 봐야 한다.

### 부수 발견 — `facebook/react` → `react/react`

GitHub API 가 `facebook/react` 요청을 **`react/react` 로 리다이렉트**한다(릴리스 URL 도 `github.com/react/react/releases/...` 로 반환). React Foundation 이관에 따른 org 이동으로 보인다. 지금은 리다이렉트가 살아 있어 조용하지만, 사내외 스크립트·문서·이슈 템플릿에 `facebook/react` 를 하드코딩해 뒀다면 갱신 대상이다.

## 생태계·트렌드

### Bun 1.4 — Rust 재작성이 실제로 출하됐다 (8/20)

[블로그](https://bun.com/blog/bun-v1.4) · [릴리스](https://github.com/oven-sh/bun/releases/tag/bun-v1.4.0). 8/13 회차 레이더에서 "Zig → Rust 전면 재작성" 을 예고편으로 다뤘는데, 이번이 **그 첫 stable 릴리스**다. 블로그가 직접 밝히기를 Claude Code 는 이미 몇 달째 Rust 포트를 쓰고 있었고 Prisma Compute 도 그 위에서 출시됐다. 숫자: Node 호환성 테스트 **1,517개 신규 통과**(`node:http`/`node:fs`/`node:cluster` 는 Node 자체 테스트 97% 통과), **유휴 CPU 1/5, 메모리 최대 35%↓, Linux 기동 50% 단축**. `Bun.Image`·`Bun.WebView`·`Bun.markdown`·`Bun.cron()` 같은 표준 라이브러리 내장 15종과 `bun test --parallel/--shard/--changed` 도 붙었다.

동작 변경 2건은 도입 전에 알아 둬야 한다 — **프로덕션 sourcemap 이 기본 비활성**(8/19 회차의 소스맵 체인 이야기와 정면으로 걸린다), **`trustedDependencies` 가 npm 레지스트리 출처만 자동 신뢰**.

## AI 소식

### Claude API — browser use tool GA + 베타 4건 승격 (8/19)

[릴리스 노트](https://platform.claude.com/docs/en/release-notes/api) · [browser use 문서](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool)

프론트엔드 개발자에게 이번 창의 최대 항목은 **`browser_toolset_20260801`** 이다. computer use 가 데스크톱 전체를 스크린샷+좌표로 다뤘다면, 이건 **브라우저 뷰포트 안**에서 돌면서 그 위에 **접근성 트리 읽기 + 엘리먼트 레퍼런스(`[ref_1]`) + `form_input` + 탭 관리**를 얹었다. 즉 "픽셀을 보고 클릭" 이 아니라 **"a11y 트리를 읽고 엘리먼트를 지목"** 한다 — 우리가 쓰는 시맨틱 마크업·`aria-label` 품질이 곧 에이전트 조작 성공률이 된다는 뜻이다.

**브라우저는 우리가 호스팅한다.** Anthropic 서버에서 도는 것이 없고, 페이지 내용은 우리가 돌려주는 `tool_result` 로만 API 에 들어간다. 기본 27개 액션 + 옵션 4개(`javascript_exec`·`file_upload`·`read_console`·`read_network`, 기본 비활성). GA 라 베타 헤더가 필요 없고 표준 과금이며, **Bedrock/Vertex/Foundry 에는 없다.**

같은 날 **computer use / Files API / Agent Skills(`/v1/skills`) / Admin API 유저 관리** 4건이 GA 로 승격됐다(전부 베타 헤더 제거). Files API 는 GA 포맷에서 `expires_in_seconds` 만료와 `page`/`next_page` 페이지네이션이 붙는데, **구 헤더를 계속 보내면 구 포맷이 유지**되므로 조용히 깨지지는 않는다.

### Claude Code 2.1.236 ~ 2.1.238 — MCP 보안이 조여졌다

[changelog](https://code.claude.com/docs/en/changelog). juunzzi-bot 운영에 직접 걸리는 변경이 셋이다.

- **프로젝트 `.mcp.json` 의 `headersHelper` 와 agent 파일 내 인라인 MCP 서버는 이제 폴더 trust 수락을 요구한다** — `claude -p` 에서도. 헤드리스로 도는 배선이 있으면 trust 상태를 확인해야 한다.
- **프로젝트/플러그인/agent 발 `headersHelper` 는 상속된 credential 환경변수 없이 실행된다.**
- **stdio MCP 서버가 `initialize` 전에 `server/discover` 를 받던 버그 수정** — lazy 서버가 세션 열 때마다 백엔드를 띄우던 문제. 부팅이 무거운 MCP 를 붙여 뒀다면 체감이 있을 변경.

그 외: 긴 인터랙티브 세션의 **무한 메모리 증가 수정**(서브에이전트 tool result 를 표시 윈도우 밖에서 해제), **LLM 게이트웨이/커스텀 base URL 경유 시 prompt caching 이 깨지던 버그 수정**(2.1.237), `ANTHROPIC_DEFAULT_MODEL`, macOS 샌드박스의 `**/.env` wildcard deny 가 allow 영역보다 우선하고 **파일 이름 변경으로 우회 불가**해짐.

## 지금 알아둘 개념

### ① 번들러 dev 모듈 그래프 — 순환 import 가 왜 "full reload" 를 부르는가

Vite 8.2.2 의 한 줄짜리 수정(#23259, `bundled-dev` 의 순환 import 를 full reload 대신 hot update 로)이 사실은 **dev 서버의 가장 중요한 자료구조**를 건드린다. 개발할 때 "왜 어떤 파일은 저장하면 즉시 바뀌고, 어떤 파일은 페이지가 통째로 새로고침되는가" 를 결정하는 게 이것이다.

**동작 원리.** dev 서버는 모듈 하나하나를 노드로, import 관계를 방향 간선으로 갖는 **모듈 그래프**를 들고 있다. 파일이 바뀌면:

1. 바뀐 모듈을 무효화한다.
2. 그 모듈이 **HMR 경계**인지 본다 — React Fast Refresh 라면 "컴포넌트만 export 하는 모듈" 이 경계다.
3. 경계면 거기서 멈추고 그 서브트리만 교체한다(= 상태 유지).
4. 경계가 아니면 **importer 를 따라 위로 전파**한다. 위로 올라가다 경계를 못 만나고 **엔트리에 닿으면 full reload** 다.

**여기서 순환이 문제가 되는 이유**: A → B → A 같은 사이클에 들어가면 "위로 전파" 가 종료 조건을 잃는다. 안전한 구현은 이때 그냥 포기하고 full reload 를 때린다 — 그래서 전파 알고리즘이 순환을 제대로 다루기 시작하면 **같은 코드에서 갑자기 HMR 이 살아난다.** 8.2.2 가 딱 그 변화다.

**실무 연결.** dev 에서 저장할 때마다 페이지가 통째로 새로고침돼 폼 입력이 날아가는 파일이 있다면, 대개 원인은 셋 중 하나다 — ① 그 모듈이 컴포넌트 말고 **상수·타입·유틸을 같이 export** 해서 Fast Refresh 경계가 깨졌거나(가장 흔하다), ② `index.ts` 배럴 파일이 사이클을 만들었거나, ③ 전파가 엔트리까지 갔거나. **`barrel export` 를 줄이는 리팩터링이 dev 체감 속도를 바꾸는 진짜 이유가 이것**이고, "번들 크기" 는 부차적이다. 우리 레포는 8.2.1 이라 이 수정 전이다 — 8.2.2 로 올린 뒤 평소 full reload 나던 파일이 어떻게 되는지 보는 게 가장 싼 실험이다.

**셀프체크**
1. 컴포넌트 파일에서 상수 하나를 같이 export 하면 왜 그 파일의 HMR 이 깨지나? (Fast Refresh 가 "이 모듈이 뭘 export 하는지" 를 어떻게 판단하는지로 답해 보기)
2. 전파가 엔트리에 닿았을 때 full reload 말고 다른 선택지가 없는 이유는?
3. 배럴 파일(`index.ts`)이 만드는 사이클은 프로덕션 번들에서도 문제인가, dev 그래프에서만 문제인가?

### ② MCP 2026-07-28 스펙 — 세션이 사라지고, 요청이 자기 맥락을 들고 다닌다

[스펙 발표](https://blog.modelcontextprotocol.io/posts/2026-07-28/) · [TS SDK v2.0.0 beta](https://github.com/modelcontextprotocol/typescript-sdk/releases)

MCP 는 원래 **stateful** 프로토콜이었다 — 클라이언트가 `initialize` 로 핸드셰이크해 프로토콜 버전과 capability 를 합의하고, 그 뒤 요청들은 그 세션에 얹혀 갔다. 이번 스펙이 **그 핸드셰이크를 없앴다.** 각 요청이 프로토콜 버전·클라이언트 아이덴티티·capability 를 `_meta` 에 실어 **독립적으로 이동**한다.

**왜 이게 큰가**: stateful 이면 원격 MCP 서버 앞에 로드밸런서를 둘 수 없다 — 같은 클라이언트의 요청이 다른 인스턴스로 가면 세션이 없어서 죽는다. 그래서 지금까지 원격 MCP 는 sticky session 이나 세션 스토어를 강제했다. stateless 가 되면 **평범한 무상태 웹 서비스처럼 배포·스케일**할 수 있다. 프로토콜 설계가 "대화" 에서 "HTTP" 쪽으로 한 칸 이동한 것이다.

함께 들어온 것들 중 실무에 걸리는 셋:
- **MRTR** — 서버가 `resultType: 'input_required'` 로 되묻고, 클라이언트가 `inputResponses` 를 붙여 재시도한다. **스트림을 붙들고 있지 않아도 중간 확인이 가능**해졌다(기존 elicitation 은 연결 유지가 전제였다).
- **캐시 가능한 list 결과** — `ttlMs`·`cacheScope`. 도구 목록을 매 세션 다시 받지 않아도 된다.
- **인가 강화** — RFC 9207 issuer 검증, **DCR(동적 클라이언트 등록) 폐기 → Client ID Metadata Documents**.

**juunzzi-bot 연결.** 이 레포의 MCP 배선은 두 종류다 — in-process stdio 서버(`src/mcp/<도구>.ts` + `registry.ts` 배열)와 **원격 http 커넥터**(notion·amplitude). stateless 전환이 직접 걸리는 건 후자다. 그리고 위 Claude Code 2.1.238 의 "stdio 서버가 `initialize` 전에 `server/discover` 를 받던 버그 수정" 은 **정확히 이 전환의 과도기 증상**이다 — 핸드셰이크가 사라지는 방향으로 가면서 클라이언트가 discover 를 먼저 던지기 시작했고, 그걸 못 받는 구현이 있었다. TS SDK v2 는 패키지를 `@modelcontextprotocol/{core,client,server,node,express,hono,fastify}` 로 쪼갰고 **`codemod` 패키지를 같이 낸다** — 이행 비용을 SDK 쪽이 인정했다는 뜻이다.

**주의**: v2 는 아직 **beta** 이고 v1 라인(1.30.0)이 살아 있다. 지금 할 일은 이행이 아니라 **읽고 우리 배선이 어디에 걸리는지 지도를 그리는 것**이다.

**셀프체크**
1. 핸드셰이크를 없애면 **매 요청의 페이로드가 커진다**. 그 비용을 무엇으로 상쇄하나?
2. `ttlMs` 로 tool list 를 캐싱하면, 서버가 도구를 런타임에 바꿨을 때 클라이언트는 언제 알게 되나? 그 창(window) 동안 잘못된 도구를 부르면?
3. DCR 폐기가 우리 http 커넥터(notion·amplitude)의 OAuth 흐름에 의미하는 바는? 지금 방식이 DCR 인가 아닌가?

## 떠오르는 스택 레이더

### ① Lynx — "웹뷰 다음의 레일", 그리고 당근이 실제로 깔았다

[당근 도입기](https://medium.com/daangn) (8/12) · [lynxjs.org](https://lynxjs.org/)

**기존 스택과 뭐가 다른가.** React Native 는 "JS 로 네이티브 뷰를 그린다" 였고, 웹뷰는 "브라우저를 통째로 얹는다" 였다. **Lynx(ByteDance)는 셋째 길이다** — 자체 렌더 엔진을 네이티브에 심고 **CSS 를 진짜로 구현**한 뒤, JS 를 두 스레드로 나눈다. 화면 첫 프레임을 그리는 코드는 **메인 스레드 전용 런타임**에서 즉시 돌고, 나머지 로직은 백그라운드 스레드로 밀린다. RN 의 고질적 "브리지 왕복 때문에 첫 화면이 늦다" 를 아키텍처 층에서 없애려는 베팅이다.

**성숙도·채택 신호.** 실험이 아니라 **성장 단계**다 — ByteDance 가 TikTok 계열에서 대규모로 돌리고 있고, 2025년 오픈소스화 이후 국내에서도 **당근이 프로덕션 채택**했다(보고된 시작 속도 개선 **Android 18% / iOS 37%**, 번들 독립 배포). 국내 대형 앱의 채택 사례가 나왔다는 게 이 항목을 레이더에 올리는 이유다 — 벤치마크가 아니라 **누가 실제로 걸었는가**가 신호다.

**지금 알아둘 이유.** 갈아탈 일은 없다. 그러나 **"UI 스레드를 논리적으로 쪼갠다" 는 아이디어는 웹으로 되돌아오고 있다** — React 의 concurrent 렌더, Server Components 의 "어느 코드가 어느 실행 환경에 속하는가", Partial Prerendering 이 전부 같은 질문의 변주다. Lynx 의 dual-thread 모델을 이해해 두면 **RSC 의 서버/클라이언트 경계를 "번들 최적화" 가 아니라 "실행 환경 분리" 로 읽게 된다.** 그 관점 전환이 이 항목의 실제 효용이다.

### ② 에이전트 하네스가 오픈소스 카테고리가 됐다 — DeepSeek Harness (`dsh`)

[GitHub](https://github.com/deepseek-ai/deepseek-harness) (8/13, **MIT**, Node.js)

**기존 스택과 뭐가 다른가.** LangChain 계열이 "체인/그래프를 조립하는 라이브러리" 였다면, `dsh` 는 **"모든 것이 플러그인" 인 하네스**를 표방한다 — 모델 어댑터·툴 레지스트리·세션 로그는 물론 **에이전트 루프 자체까지 교체 가능**하다. 즉 프레임워크가 루프를 소유하지 않는다. Ollama 가 `ollama launch dsh` 로 통합한 것도 이 층이 "런타임" 으로 굳는 중이라는 신호다.

**성숙도.** **실험 단계다.** 저장소 스스로 개발자 프리뷰이며 호환성 깨지는 변경을 예고한다. 스타 수는 소스마다 95K/174K 로 어긋나 신뢰하지 않는다(8/15 회차의 "절대 수치를 믿지 않는다" 규율 적용). 지금 채택 근거는 인기가 아니라 **모델 벤더가 직접 런타임을 낸다는 사실 자체**다.

**지금 알아둘 이유 — juunzzi-bot 과 정면으로 겹친다.** 이 봇은 SQLite 내구 잡 큐 + Socket Mode 복원력 + registry 배열 기반 도구 경계를 **직접 짠 하네스**다. `dsh` 를 읽는 값어치는 이식이 아니라 **비교**에 있다: ① 상태 지속성(우리는 SQLite, 저쪽은 세션 로그 플러그인) ② 재시작 복구 ③ 도구 권한 경계. 세 축에서 대조해 보면 "남이 만든 런타임을 안 쓰기로 한 선택" 이 무엇을 얻고 무엇을 포기한 것인지 남에게 설명할 수 있게 된다. 8/13 회차 기준으로 그 비교가 아직 안 돼 있다.

### MCP 2026-07-28 스펙 — stateless 전환이 우리 배선 어디에 걸리는지 지도 그리기

**시작점**: [스펙 발표 글](https://blog.modelcontextprotocol.io/posts/2026-07-28/) → [TS SDK v2.0.0 릴리스 노트](https://github.com/modelcontextprotocol/typescript-sdk/releases) → `src/mcp/registry.ts` 와 http 커넥터 배선

**왜 오늘인가 — 세 신호가 같은 방향을 가리킨다.**

1. Claude Code 2.1.238 이 **stdio 서버의 `initialize` 이전 `server/discover` 버그**를 고쳤다. 이건 잡버그가 아니라 **핸드셰이크가 사라지는 전환의 과도기 증상**이다 — 클라이언트가 이미 새 스펙 쪽으로 움직이고 있다.
2. 같은 릴리스가 **`headersHelper` 의 신뢰 경계를 조였다**(폴더 trust 요구, credential 환경변수 미상속). 인증 방식 변화(DCR 폐기 → Client ID Metadata Documents)와 같은 축이다.
3. SDK 가 **`codemod` 패키지를 동봉**했다. 이행이 자동화가 필요할 만큼의 규모라는 걸 만든 쪽이 인정한 것이다.

**오늘 할 일은 이행이 아니다**(v2 는 beta, v1 은 1.30.0 으로 살아 있다). **지도를 그리는 것**이다: 우리 in-process stdio 도구들은 세션 상태를 실제로 쓰고 있나, 아니면 이미 사실상 stateless 인가? http 커넥터(notion·amplitude)의 OAuth 는 DCR 경로인가? tool list 를 `ttlMs` 로 캐싱하면 registry 배열을 바꿨을 때 클라이언트가 언제 알게 되나?

**셀프체크**
1. 핸드셰이크를 없애면 매 요청 페이로드가 커진다 — 그 비용은 무엇으로 상쇄되나? (힌트: 로드밸런서)
2. MRTR(`input_required` → `inputResponses` 재시도)이 기존 elicitation 과 결정적으로 다른 점은? 스트림을 안 붙들어도 되는 게 왜 중요한가?
3. `registry.ts` 배열이 곧 노출 경계라는 이 레포의 규율은, tool list 가 클라이언트에 캐싱되기 시작하면 어떤 새 실패 모드를 갖게 되나?
