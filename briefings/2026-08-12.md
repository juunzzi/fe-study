# FE/AI 브리핑 — 2026-08-12

## TL;DR

- **Vitest 5.0.0-rc.1**(8/11)이 나왔다. `await` 안 붙인 비동기 assertion 이 이제 **테스트를 실패시킨다** — 우리 레포(4.1.9)가 올릴 때 가장 먼저 터질 지점이다.
- **Turbopack 이 CJS tree-shaking 기본 활성화를 되돌렸다**(16.3.1 canary). 번들러가 CJS 모듈 그래프를 어디까지 못 믿는지가 드러난 사건 — 오늘의 개념 ②로 풀었다.
- Vercel 이 **`Bun.serve` 를 함수 엔트리포인트로** 받기 시작했다(WebSocket 포함). 과금이 유휴 연결이 아니라 **메시지 처리 시간** 기준이라 실시간 서버의 원가 구조가 바뀐다.
- **Claude Sonnet 5 의 9/1 가격 인상($2/$10 → $3/$15)이 취소**됐다. AI 기능 원가 산정을 다시 안 해도 된다.
- 오늘의 학습 추천은 **React Compiler** — 우리 `lbox-client` 에 이미 `reactCompiler: true` 로 켜져 있고, 팀이 이미 이것 때문에 한 번 데였다.

## 스택 업데이트

### Vitest 4.1.9 → 5.0.0-rc.1 ([릴리스](https://github.com/vitest-dev/vitest/releases/tag/v5.0.0-rc.1), 8/11)
- **breaking**: `await` 하지 않은 비동기 assertion 이 이제 테스트를 실패시킨다. `-t` 필터 구분자가 `>` 로 바뀌고, `only` 는 1회만 계산된다.
- inline project 가 기본으로 루트 config 를 상속하고 nested project 를 지원한다. inline project 끼리 Vite 서버를 공유한다. fake timers 없이 Temporal mocking 가능.
- `--typecheck` 가 tsc 크래시를 false success 로 보고하던 버그 수정 — **타입 테스트가 조용히 통과하고 있었을 수 있다.**
- 우리 레포 영향: RC 라 지금 올릴 것은 아니다. 다만 "await 없는 assertion" 은 **지금 4.x 에서 미리 훑어 고쳐 두면** 나중에 무통증으로 넘어간다. 4.x 최신은 4.1.10(7/6).

### Next.js 16.2.10 → (stable 16.3.0 유지, 16.3.1 canary 진행 중) ([releases](https://github.com/vercel/next.js/releases), 8/10~8/11)
- **Turbopack CJS tree-shaking 기본 활성화 revert**([#97018](https://github.com/vercel/next.js/pull/97018)). `var x = module.exports = {}` 패턴에서 tree-shaking 을 bail 하도록 바꾸고, scope hoisting 을 위한 CJS 분석을 따로 추가했다. 스테일 캐시 버전에 TTL 도입.
- prefetch 루프를 유발하던 optimistic routing 버그 수정([#97128](https://github.com/vercel/next.js/pull/97128)), **legacy PPR 코드 경로 제거** — Cache Components 가 내부 PPR 시그널을 정식으로 대체했다.
- 우리 레포 영향: 여전히 16.2.10 → **16.3.0 stable 로 올릴지가 미결 안건**(8/6 브리핑 참조). 16.3.1 은 아직 canary 뿐.

### Rspack 2.1.9 ([릴리스](https://github.com/web-infra-dev/rspack/releases/tag/v2.1.9), 8/11)

### ① React Compiler — 우리 앱에서 이미 돌고 있는데, 무엇을 하고 있는지

**무엇인가.** React Compiler 는 빌드 타임에 컴포넌트/훅을 분석해 **`useMemo`·`useCallback`·`React.memo` 를 자동으로 넣는** 컴파일러다. 정확히는 렌더 결과를 캐시 슬롯 배열에 저장하고, 입력이 바뀐 슬롯만 다시 계산하는 코드로 다시 쓴다. 전제는 **React 규칙(Rules of React)을 지킨 코드**다 — 렌더 중 순수해야 하고, props/state 를 변형하지 않아야 한다. 규칙을 어긴 코드는 컴파일러가 **조용히 최적화를 포기(bail out)** 하거나, 더 나쁘게는 런타임 동작이 달라진다.
([공식 문서](https://react.dev/learn/react-compiler), [설치·설정](https://react.dev/learn/react-compiler/installation))

**왜 지금.** ① 우리 `apps/lbox-client/next.config.ts` 에 `reactCompiler: true` 가 이미 켜져 있고 `babel-plugin-react-compiler@^1.0.0` 이 물려 있다 — **모르고 쓰는 상태가 가장 위험한 구간**이다. ② 팀 메모리에 따르면 yunjunseo 님이 2026-07-20 에 정확히 이걸로 데인 기록이 있다: React Compiler 가 켜진 환경에서 `useEffect(() => { setState(storage.read()) }, [])` 로 클라이언트 전용 스토리지(sessionStorage/localStorage)를 읽어 state 에 반영하면 *"Cannot call setState synchronously within an effect"* 류 문제가 난다는 것. 컴파일러가 없을 땐 통과하던 패턴이 컴파일러 아래서 깨지는 대표 사례다.

**실코드 연결.** ① `next.config.ts:35` 의 `reactCompiler: true` 가 실제로 무엇을 켜는지 → Next 는 이걸 babel 플러그인 경유로 태운다(그래서 그 파일들만 SWC 대신 babel 을 탄다 — **빌드 시간에 영향이 있다**). ② `eslint-plugin-react-hooks` 의 컴파일러 룰이 우리 `eslint.config.mjs` 에 켜져 있는지 확인 — 컴파일러가 bail out 한 컴포넌트를 알려주는 유일한 신호다. ③ 우리 코드에서 아직 손으로 남아 있는 `useMemo`/`useCallback` 이 지금도 필요한 것인지, 컴파일러와 중복인지.

**셀프체크**: ① 컴파일러가 최적화를 포기하는(bail out) 조건은 무엇이고, 포기했다는 걸 어떻게 아는가? ② 컴파일러가 넣는 메모이제이션과 내가 손으로 쓴 `useMemo` 의 캐시 무효화 기준은 같은가 다른가? ③ 위 sessionStorage 사례에서, 컴파일러가 있든 없든 안전한 패턴은 무엇인가?

### ② 번들러의 모듈 그래프 — CJS 는 왜 tree-shaking 이 어려운가

**무엇인가.** tree-shaking 은 "안 쓰는 코드 지우기"가 아니라 **모듈 그래프에서 도달 불가능한 export 를 정적으로 증명해 지우는 것**이다. ESM 은 `import`/`export` 가 **정적 선언**이라 그래프를 파싱만으로 그릴 수 있다. CJS 는 `module.exports` 가 그냥 **런타임 객체 대입**이라 그래프가 실행 전엔 확정되지 않는다 — `module.exports[key] = fn` 한 줄이면 정적 분석이 무너진다. 그래서 번들러는 CJS 를 만나면 보수적으로 "전부 살아있다"고 가정한다. scope hoisting(모듈을 하나의 스코프로 합쳐 함수 래퍼를 없애는 최적화)도 같은 이유로 CJS 에선 조건이 까다롭다.

**왜 지금.** 이번 주 Turbopack 이 **CJS tree-shaking 기본 활성화를 revert** 했고([#97018](https://github.com/vercel/next.js/pull/97018)), 동시에 `var x = module.exports = {}` 패턴에서 bail 하는 처리와 scope hoisting 용 CJS 분석을 따로 넣었다. 지난주엔 esbuild 가 **TS import alias 때문에 오탐 tree-shaking** 을 하던 버그를 고쳤다. 즉 "번들러가 알아서 잘 지워주겠지"가 성립하지 않는 구간이 실재하고, 그 경계가 지금 활발히 움직이는 중이다. 번들 크기가 왜 그 모양인지 설명 못 하면 최적화는 주술이 된다.
([Next.js releases](https://github.com/vercel/next.js/releases), [Turbopack 문서](https://nextjs.org/docs/app/api-reference/turbopack))

**실코드 연결.** 우리 `lbox-client` 는 dev 를 `next dev --turbopack` 으로 돌린다. 의존성 중 CJS-only 로 배포되는 것들(예: `@react-pdf-viewer/*`, `crypto-js`, `jsonwebtoken`)이 번들에 통째로 들어오고 있는지 — `next build` 의 First Load JS 와 번들 분석으로 확인할 수 있다. `es-toolkit`·`date-fns` 처럼 ESM 우선 패키지로 갈아탄 자리가 왜 효과가 있었는지도 같은 원리다.

**셀프체크**: ① `import * as x from 'cjs-pkg'` 와 named import 는 번들러에게 무엇이 다른가? ② `"sideEffects": false` 는 정확히 무슨 약속이고, 틀리면 어떤 버그가 나는가? ③ scope hoisting 이 되면 왜 파일이 작아지는가(단순히 래퍼 함수가 빠지는 것 말고)?

## 떠오르는 스택 레이더

### Effect (TypeScript) — 에러와 의존성을 타입 시그니처 안으로

- **뭐가 다른가**: `Promise`/`try-catch` 는 에러를 타입 밖에 둔다. Effect 는 `Effect<Success, Error, Requirements>` 3-파라미터로 **에러와 의존성을 타입에 올린다.** TanStack Query 가 "서버 상태의 캐싱·재시도·무효화"를 훅 레벨에서 푸는 것과 달리, Effect 는 재시도·타임아웃·인터럽션·리소스 정리·구조적 동시성을 **합성 가능한 값**으로 다룬다. DI 는 컨테이너가 아니라 타입 `R` 채널이라, 서비스를 안 넣으면 컴파일이 안 된다.
- **성숙도·채택 신호**: 안정판 `effect@3.22.1`(7/30), **v4 는 베타 진행 중**(`4.0.0-beta.107`, 8/10 — 정식 날짜 미확인). npm 주간 다운로드 26.7M, GitHub 스타 15.2K. Thoughtworks Radar **Trial** 링(Vol.34). ⚠️ core 26.7M 중 상당량이 전이 의존성이라 **실질 채택은 `@effect/platform` 곡선(월 2.07M → 6.58M, 3.2배)에 가깝다** — core 숫자를 그대로 인용하지 말 것.
- **지금 알아둘 이유**: AI 에이전트 코드가 늘면서 재시도·타임아웃·부분 실패·리소스 해제가 앱 코드의 주 부담이 됐고, "에러를 타입에 올린다"가 곧 코드리뷰 어휘가 된다.
- [effect.website](https://www.effect.website/) · [Thoughtworks Radar](https://www.thoughtworks.com/radar/languages-and-frameworks/effect)

### Sync engine / local-first 데이터 레이어 (TanStack DB, Zero)

- **뭐가 다른가**: TanStack Query 는 **요청 단위 캐시**다 — queryKey 로 응답을 캐싱하고 invalidate 로 다시 당긴다. Sync engine 은 캐시 대상을 응답이 아니라 **쿼리 결과 집합**으로 바꾼다. **Zero** 는 앱 코드에 쓴 쿼리가 곧 동기화 범위인 query-driven sync 이고, 읽기·쓰기가 로컬에 먼저 히트한 뒤 백그라운드로 서버와 맞춘다. **TanStack DB** 는 TanStack Query 위에 collection + live query 를 얹는데, live query 가 **differential dataflow** 라 전체 재실행이 아니라 증분 갱신이다(공식 문서 기준 10만 건 정렬 컬렉션에서 1행 갱신 ~0.7ms). 낙관적 상태를 동기화 데이터와 분리 보관해 **실패 시 자동 롤백**된다.
- **성숙도·채택 신호**: `@tanstack/db` 0.6.17(7/24), 주간 588K, 스타 3.9K — 월간 27.7K(25년 8월) → 2.0M(26년 7월)로 **약 72배**. 단 **아직 0.x** 라 API 안정 선언 없음. `@rocicorp/zero` 1.8.0(7/13), 주간 101K — **1.0 이 2026-06-08** 로 알파 2년을 끝냈다. 한계도 공식 문서에 명시돼 있다: Postgres 전용, 100GB 미만 권장, **오프라인 쓰기 미지원**(엄밀히 local-first 가 아니라 서버 권위형), 클라이언트 번들 718KB(비압축). 큰 회사 도입 사례는 미확인(zbugs·Productlane·Ranger 정도).
- **지금 알아둘 이유**: 진입로가 하필 **TanStack Query 바로 위 레이어**라 우리 스택에서 한 발이면 닿는다. **낙관적 업데이트 롤백과 컬렉션 join 을 손으로 짜고 있다면 그게 이미 이 문제의 증상이다.**
- [TanStack DB 개요](https://tanstack.com/db/latest/docs/overview) · [Zero — When To Use](https://zero.rocicorp.dev/docs/when-to-use)
