## 스택 업데이트

### ESLint `^9.39.5` → **10.8.1** — 우리는 `maintenance` 태그에 고정돼 있다

이번 회차에서 가장 실질적인 발견이다. npm 레지스트리의 dist-tags를 직접 확인했다:

```
eslint tags: { "latest": "10.8.1", "maintenance": "9.39.5", "next": "10.0.0-rc.2" }
```

`9.39.5`(2026-07-10)는 최신이 아니라 **유지보수 라인의 최신**이다. `latest`는 **10.8.1(2026-08-07)**. 지난주 TypeScript에서 밟았던 함정 — "레포 릴리스 페이지만 보면 6.0.3이 최신으로 보인다" — 과 **같은 종류의 함정을 다른 패키지에서 또 밟고 있었다.** 그때 배운 교훈("모니터링 소스를 바꾼다")이 ESLint에는 적용이 안 돼 있었던 것이다.

**우리 영향**: 지금 깨지는 건 없다. 다만 우리 lint 설정 패키지가 `@eslint/js ^9.39.5` + `typescript-eslint ^8.66.0` + `eslint-plugin-react-hooks ^7.1.1` 조합이라, ESLint 10으로 올리려면 이 셋의 peer 호환을 한 번에 맞춰야 한다. **10의 구체적 breaking 목록은 이번 조사에서 확인하지 못했다 — 미확인.** 다음 회차에서 마이그레이션 가이드를 따로 확인할 항목으로 남긴다.

### Vitest 4.1.10 → **5.0.0-rc.2** (2026-08-17)

([릴리스](https://github.com/vitest-dev/vitest/releases/tag/v5.0.0-rc.2)) v5 정식 직전 두 번째 RC. 신규 기능은 GitHub Actions 리포터 요약 타이틀 커스터마이징 하나뿐이고 나머지는 안정화 — 테스트 라이프사이클 전역 동시성 제한 복구, 브라우저 모드 graceful disconnect, strict CSP 하 스냅샷 평가 수정, config root 해석 수정. **rc.1 → rc.2에 breaking change는 없다**(v5 메이저 전체의 breaking은 별건).

**우리 영향**: 없음, 아직은. 다만 vitest 설정이 13개(앱 9 + 패키지 4)라 v5 메이저는 한 번에 다 건드리는 작업이 된다. RC가 rc.2까지 왔다는 건 준비를 시작할 시점이라는 뜻이다.

### Next.js 16.3.0 → **16.3.1** (2026-08-13) — 아직 안 올렸다

패치, breaking 없음. 창 밖(8/13)이지만 우리는 여전히 `16.3.0`에 있다. 창 안에는 canary 둘이 있었다 — [16.3.1-canary.21](https://github.com/vercel/next.js/releases/tag/v16.3.1-canary.21)(AsyncLocalStorage 인스턴스를 global symbol에 고정, `concurrentRouterQueue` 플래그 스캐폴딩), [canary.22](https://github.com/vercel/next.js/releases/tag/v16.3.1-canary.22)(turbo-persistence의 32비트 usize 변환 수정, persistence GC). 둘 다 사용자 대면 기능 없음.

## 지금 알아둘 개념

### ① `<ViewTransition>` — 애니메이션이 "컴포넌트 안"이 아니라 **두 커밋 사이**로 옮겨진다

**무엇인가.** 우리가 아는 애니메이션은 전부 **살아 있는 엘리먼트를 프레임마다 움직이는 것**이다. Framer Motion의 layout animation이 대표적이다 — 라이브러리가 mount/unmount 라이프사이클과 요소 위치를 계속 추적하고, 요소 하나하나가 자기 위치를 애니메이트한다.

View Transitions는 층위가 다르다. 브라우저가 **커밋 직전 화면을 정적 스냅샷(`::view-transition-old`)으로 떠 두고**, React가 DOM을 한 번에 갈아끼운 뒤, 새 상태의 라이브 스냅샷(`::view-transition-new`)과 그 둘 **사이만** 애니메이트한다. 즉 애니메이션 대상이 컴포넌트 트리가 아니라 **두 커밋 사이의 이미지 쌍**이다.

이 한 문장이 왜 중요하냐면 — 라우트가 통째로 바뀌어서 **두 화면에 살아남는 공통 React 인스턴스가 하나도 없어도** 이어진 애니메이션이 나온다. 목록의 썸네일과 상세의 히어로 이미지가 서로 다른 컴포넌트여도 `name`만 같으면 브라우저가 짝을 맺어 이어 준다. 기존 방식으로는 두 트리 사이를 잇는 인스턴스가 없어서 가장 어려웠던 지점이다.

**대가도 명확하다.** React 공식 문서가 직접 적어 뒀다 — 스냅샷 하나를 스케일·이동·크로스페이드하므로 **안쪽 요소들이 각자 움직이지 않는다**. 성능과 연속감은 좋아지지만 입자성을 잃고, 따로 움직여야 할 게 있으면 `<ViewTransition>` 경계를 손으로 더 잘게 나눠야 한다. 그리고 대체재가 아니다: 문서는 "navigation, expanding, opening, re-ordering 같은 **UI 전환**에 쓰라"고 명시하고, 좋아요 버튼 피드백이나 스켈레톤 글리머 같은 단일 요소 애니메이션은 여전히 CSS 애니메이션이 맞는 도구라고 못 박는다.

**발동 조건이 이 API의 진짜 핵심이다.** 레퍼런스 원문:

> "By default, `setState` updates immediately and does not activate `<ViewTransition>`, only updates wrapped in a Transition, `<Suspense>`, or `useDeferredValue` activate ViewTransition."

트리거는 셋뿐이다 — `startTransition`, `useDeferredValue`, `<Suspense>` fallback→content. **`<Activity>` 토글은 별도 트리거가 아니라** 이 트리거들 안에서 enter/exit로 해석되고, **navigation도 React 자체 트리거가 아니다** — 라우터가 네비게이션을 Transition으로 감싸기 때문에 발동한다. 여기서 지난 두 회차가 한 줄로 이어진다: [Suspense 경계는 스트리밍 단위](./2026-08-10.md)고, [`<Activity>`는 언마운트 대신 숨기기](./2026-08-13.md)이며, ViewTransition은 **그 둘이 만드는 커밋 경계에 애니메이션을 붙이는 층**이다. 세 API가 따로 있는 게 아니라 같은 축의 세 지점이다.

애니메이션 종류는 React가 휴리스틱으로 판정한다 — `enter`(이 Transition에서 처음 삽입), `exit`(처음 삭제), `update`(내부 DOM 변경 또는 형제 때문에 경계 자체의 크기·위치 변경), `share`(삭제 서브트리와 삽입 서브트리에 **같은 `name`**이 있으면 shared element transition).

**상태는 정확히 알고 있어야 한다 — stable이 아니다.** [레퍼런스](https://react.dev/reference/react/ViewTransition) 상단 배너 그대로 "currently only available in React's Canary and Experimental channels"다. [React 19.2 릴리스 글](https://react.dev/blog/2025/10/01/react-19-2)에 ViewTransition은 **기능으로 실려 있지 않고**, 딱 한 번 미래형으로만 언급된다. 19.2에 stable로 들어간 건 `<Activity>` 쪽이다.

그런데 **Next.js App Router는 React canary를 쓴다.** [공식 가이드](https://nextjs.org/docs/app/guides/view-transitions): "View transitions work in the App Router with **no configuration**. The App Router uses React canary releases… You do not need to install `react@canary` yourself." 15.2에 있던 `experimental.viewTransition` 플래그는 현재 문서(16.3.1)에서 **사라졌다** — 기본 동작이 됐다. 대신 [`<Link transitionTypes={['slide-in']}>`](https://nextjs.org/docs/app/api-reference/components/link#transitiontypes)가 **16.2.0**에 추가돼, 네비게이션 Transition 안에서 `React.addTransitionType`으로 전달된다. 즉 **바닐라 React 앱은 canary를 직접 깔아야 하지만, App Router 앱은 이미 쓸 수 있는 상태**다.

**왜 지금 / 실코드 연결.** 우리 코드베이스는 디자인 시스템 패키지 셋과 앱에 `framer-motion ^12.43.0`을 물고 있고, `ViewTransition`/`viewTransition` 사용처는 **0건**이다(확인함). 그리고 우리는 Next 16.3.x — 즉 **플래그도 canary 설치도 필요 없이 지금 당장 쓸 수 있는 자리에 있으면서 아직 안 쓰고 있는** 상태다. 여기서 판단해야 할 건 "갈아탈까"가 아니다. framer-motion은 컴포넌트 내부 인터랙션(호버·드래그·프레젠스)에서 계속 최선이고, ViewTransition이 이기는 건 **라우트 전환과 목록↔상세 shared element** 딱 그 구간이다. 경계를 어디 그을지가 결정이고, 그러려면 발동 조건 셋을 정확히 알아야 한다.

**놓치기 쉬운 함정 넷** (전부 공식 문서 명시):
- **최상위 배치 제약** — "`<ViewTransition>` only activates exit/enter if it is placed *before* any DOM nodes." ViewTransition 위에 `<div>` 하나만 감싸도 enter/exit가 조용히 안 뜬다.
- **`name` 중복은 전환을 통째로 스킵시킨다** — MDN: 같은 `view-transition-name`이 동시에 둘이면 `ViewTransition.ready`가 reject되고 **transition이 스킵된다**. 그래서 React는 `name`을 안 주면 자동으로 고유 이름을 만들고, 문서는 **shared element 외의 용도로 `name`을 쓰지 말라**고 한다.
- **뷰포트 밖이면 짝이 안 맺힌다** — shared element 한쪽이 화면 밖이면 페어링이 안 된다. 리스트 재정렬은 `name`이 아니라 **key**로 identity를 유지해야 한다.
- **`prefers-reduced-motion`을 React가 안 꺼 준다** — 문서가 명시적으로 "React doesn't automatically disable animations for this case"라고 적고 미디어 쿼리로 직접 끄라고 권한다. 접근성 회귀가 조용히 들어오는 자리다. 보너스로 `::view-transition { pointer-events: none; }`도 권장된다(전환 중 오버레이가 포인터를 먹는다).

**셀프체크**
1. `setState`를 `startTransition`으로 감싸지 않으면 `<ViewTransition>`은 왜 발동하지 않는가? 브라우저의 `startViewTransition`이 요구하는 계약과 연결해서 설명해 보라.
2. 목록 → 상세로 넘어갈 때 썸네일이 히어로 이미지로 이어지게 하려면 무엇을 어디에 붙여야 하는가? 그리고 그 목록이 스크롤돼 썸네일이 화면 밖에 있으면 어떻게 되는가?
3. framer-motion의 layout animation과 ViewTransition이 같은 화면에서 충돌한다면 어느 층에서 부딪히는가? 둘 중 무엇을 어떤 구간에 남길 것인가?
4. `default="none"`을 주면 무엇이 꺼지고 무엇이 남는가?

### ② 짧게 — `flushSync`가 끼면 Transition이 통째로 스킵된다

위 개념의 곁가지지만 독립적으로 알아둘 값어치가 있다. React는 view transition이 **동기적으로 완료 가능**하다는 전제에 의존하는데, 중간에 `flushSync`가 끼면 그 전제가 깨져서 **Transition을 건너뛴다**. 서드파티 라이브러리(특히 구형 애니메이션·측정 코드)가 내부에서 `flushSync`를 부르는 경우가 있어서, "왜 애니메이션이 가끔 안 나오지"의 원인이 자기 코드 밖에 있을 수 있다. 같은 결로 `<ViewTransition>` 이벤트 콜백(`onEnter` 등)은 **반드시 cleanup 함수를 반환해야** 중단 시 브라우저가 애니메이션을 취소할 수 있다.

- **[Kimi K3 (Moonshot)](https://vllm.ai/blog/2026-07-22-kimi-k3-preview)** — **2.8T 총 파라미터**, 라우티드 전문가 896개 중 토큰당 16개 활성 + 공유 전문가, **1M 컨텍스트**, 네이티브 비전. vLLM 공식 블로그로 확인된 값이다. 새 어텐션 KDA(Kimi Delta Attention) + AttnRes를 쓰고 4레이어마다 MLA를 섞는 하이브리드. *활성 파라미터 104B는 2차 출처에만 있고 공식 확인 못 함.*
- **[GLM-5.2 (Z.ai, MIT)](https://huggingface.co/zai-org/GLM-5.2)** — **가장 관대한 라이선스로 가장 큰 모델을 푸는** 베팅. IndexShare 스파스 어텐션으로 1M 컨텍스트에서 토큰당 FLOPs를 2.9배 줄였고, thinking-effort 레벨을 노출해 깊이/지연을 교환할 수 있다. **파라미터가 출처마다 어긋난다** — HF 카드는 753B, 다수 2차 출처는 744B 총 / 40B 활성. 컨텍스트도 "1M" vs "실사용 256K"로 갈린다.
- **[Qwen3.8-Max 오픈웨이트](https://llm-stats.com/blog/research/qwen3-8-max-open-weights)** (8/12) — Qwen이 Max급을 처음 다운로드 가능하게 풀었다. 다만 **Apache 2.0이 아니라 레비뉴 셰어 조항이 들어간 커스텀 라이선스**라, "오픈웨이트"라는 말의 의미가 갈라지는 지점이다. *공식 모델 카드를 직접 열지 못했고 2차 출처끼리 컨텍스트·모달리티가 어긋난다 — 확인 못 함.*

**[MCP 2026-07-28 스펙](https://blog.modelcontextprotocol.io/posts/2026-07-28/)** — 프로토콜 코어가 **스테이트리스**로 바뀌었다. Streamable HTTP에서 프로토콜 레벨 세션과 `Mcp-Session-Id` 헤더가 제거되고, 헤더 기반 라우팅·캐시 가능한 list 결과·Multi Round-Trip Requests가 들어갔다. 프론트엔드 관점에서 큰 건 **MCP Apps** — 서버가 샌드박스 iframe에 렌더되는 인터랙티브 HTML UI를 배포하고, 툴이 UI 템플릿을 미리 선언해 프리페치·캐싱·보안 리뷰가 가능해진다. **Tasks 확장**은 툴 호출에 task 핸들로 응답하고 `tasks/get`·`tasks/update`·`tasks/cancel`로 몰아가는 장시간 작업 모델이다. Python SDK 2.0이 같은 날 나오며 대부분의 서버가 상속하던 클래스 이름을 바꿨다 — **파괴적 변경**이다.

> juunzzi-bot은 MCP 서버를 여럿 물고 있으므로, "세션이 프로토콜에서 빠졌다"는 변화는 언젠가 배선을 건드린다. 지금 할 일은 아니고, 스펙이 어느 방향으로 갔는지만 알고 있으면 된다.

## 떠오르는 스택 레이더

**측정 기준 먼저.** [8/15 회차](./2026-08-15.md)에서 세운 규율대로 절대 다운로드는 쓰지 않는다. 실측으로도 `react`는 191.4M(2025-08) → 642.1M(2026-08)으로 **3.35배**, `typescript`는 389.5M → 1000.6M으로 **2.57배** 부풀었다 — **인플레이션 배율조차 패키지마다 다르다.** 아래는 전부 같은 시점 react 또는 typescript 대비 비율이다.

### ① 클라이언트 사이드 쿼리 엔진 — TanStack Query "위에 얹히는 층"

**무엇을 다르게 푸는가.** TanStack Query는 근본적으로 **요청-응답 캐시**다. 키가 있고, 그 키에 응답 JSON이 붙고, invalidate하면 다시 fetch한다. 그래서 "이 필터 조건에 맞는 항목만", "두 리소스를 조인해서", "낙관적 업데이트가 목록·상세·카운트에 동시 반영"은 전부 손으로 짜는 캐시 수술(`setQueryData` + 수동 invalidate 그래프)이 된다.

[TanStack DB](https://tanstack.com/db/latest/docs/overview)는 그 자리에 **정규화된 컬렉션 + 라이브 쿼리**를 놓는다. 서버 통신은 여전히 TanStack Query가 하고(**대체가 아니라 위에 얹는 층이다**), 받아온 데이터가 컬렉션에 정규화되어 들어가며, 컴포넌트는 `useLiveQuery`로 filter/join/order/group을 건다. 핵심은 재실행이 아니라 **증분 갱신** — d2ts(differential dataflow의 TS 구현)로 바뀐 행만 전파해 "10만 건 정렬 컬렉션에서 1행 수정 ~0.7ms(M1 Pro)"를 주장한다. 낙관적 업데이트도 캐시 다섯 군데를 손으로 고치는 게 아니라 컬렉션 한 곳을 고치면 그걸 보는 모든 라이브 쿼리가 따라온다. [Zero](https://zero.rocicorp.dev/docs/when-to-use)는 한 발 더 나가 **쿼리 자체를 동기화 단위로** 만든다.

**성숙도 — 실험 후반. 방향은 진짜, 크기는 아직 작다.**

| 패키지 | 2025-08 (vs react) | 2026-08 (vs react) | 정규화 성장 |
|---|---|---|---|
| `@tanstack/db` | 0.014% | **0.331%** | **약 23배** |
| `@electric-sql/client` | 0.169% | 0.587% | 약 3.5배 |
| `@rocicorp/zero` | 0.052% | 0.058% | **약 1.1배 (정체)** |
| `yjs` (성숙 CRDT 대조군) | — | 4.70% | — |

가장 정직한 비교는 같은 배급 경로 안에서 재는 것이다 — `@tanstack/db` ÷ `@tanstack/react-query`는 **0.05% → 0.83%로 약 17배**. 방향은 가파르지만 **절대 위치는 TanStack Query 설치 120건 중 1건**이다. GitHub도 같은 말을 한다: [TanStack/db](https://github.com/TanStack/db) 3,866 스타 vs [TanStack/query](https://github.com/TanStack/query) 50,148 (8%).

**과대평가를 깎을 곳 둘.** 첫째, **Zero가 담론량 대비 가장 크게 부풀어 있다.** [2026년 6월 1.0](https://www.infoq.com/news/2026/06/zero-version-1/)을 찍었고 [싱크 엔진 비교글들](https://johnny.sh/blog/choosing-a-sync-engine-in-2026/)이 대체로 승자로 꼽지만 **정규화 다운로드는 1년간 1.1배 — 통계적으로 제자리**다. 1.0 자체도 InfoQ 표현으로 "breaking change 없는 사실상 상징적 버전 범프"였고, 제약이 무겁다(Postgres 전용, Postgres view 미동기, **SSR 미지원**, 클라이언트 번들 718KB 비압축). 둘째, **"프로덕션 준비됨"은 아직 아니다.** TanStack DB는 2025년 12월 1.0 목표를 놓치고 현재 **0.7.x**, 0.6의 persistence는 스스로 "first alpha"라 적었고 SSR은 design partner 모집 단계다. 채용 신호는 거의 0. 현장 후기도 마케팅보다 훨씬 거칠다 — 제품 코드보다 충돌 해결 코드를 더 많이 짰다는 기록이 계속 나온다([Smashing, 2026-05](https://www.smashingmagazine.com/2026/05/architecture-local-first-web-development/)). 참고로 **이 판 전체(`@tanstack/db` + electric + zero 합계)가 `yjs` 하나의 1/5**다. 로컬 퍼스트 담론의 크기는 로컬 퍼스트 채택의 크기가 아니다.

**지금 알아둬야 할 이유 한 줄.** 프레임워크 교체 후보가 아니라 **이미 쓰는 TanStack Query의 다음 층**이라, "캐시 무효화 그래프를 손으로 관리하는 코드"가 늘어나는 화면이 생기는 순간이 이 개념이 필요해지는 시점이다. 도입 트리거는 `@tanstack/db`의 **1.0 + SSR 지원**으로 잡아두면 된다.

### ② 실브라우저 컴포넌트 테스트 (Vitest Browser Mode)

**무엇을 다르게 푸는가.** React 개발자의 기본값은 10년째 **jsdom + React Testing Library**, 즉 "브라우저를 JS로 흉내 낸 것" 위에서 컴포넌트를 검증하는 것이다. 대가는 다 안다 — `IntersectionObserver`가 없어 모킹하고, `getBoundingClientRect`가 전부 0이라 가상 스크롤·플로팅 UI를 못 재고, CSS가 적용되지 않으니 **"보이는가"를 물을 수 없고**, hover·focus·포인터·클립보드가 실제와 다르다. 결국 레이아웃·시각이 걸린 테스트만 골라 E2E(Playwright)로 밀어내고, **그 사이에 낀 컴포넌트 층이 검증 공백**으로 남는다.

[Vitest 4.0에서 stable이 된 Browser Mode](https://voidzero.dev/posts/announcing-vitest-4)는 이 이분법 자체를 없앤다. 같은 Vitest 러너·같은 watch 루프·같은 `expect` 안에서 테스트가 **진짜 Chromium/Firefox/WebKit에 렌더**되고, 상호작용은 Playwright의 locator/user-event API로 하며, **시각 회귀(스크린샷 비교)와 Playwright trace가 유닛 테스트 계층으로 내려온다**([릴리스](https://vitest.dev/blog/vitest-4)). 서버를 띄우고 라우팅을 태우는 E2E가 아니라 **컴포넌트 하나를 실제 렌더링 엔진에 마운트**하는 것이라, 속도와 격리는 유닛 쪽에 남는다. RTL도 계속 쓸 수 있지만 공식 권장은 [vitest-browser-react](https://vitest.dev/api/browser/react)로, `act()` 래핑과 `waitFor` 재시도 대신 **내장 locator의 자동 재시도**에 맡기는 모델이다.

**성숙도 — 두 겹으로 나눠 봐야 한다.** 바깥 껍질(Vitest 자체)은 **이미 이겼다.** typescript 대비로 정규화하면 `vitest` 15.2% → **35.6%(2.35배)**, `jest` 34.0% → **18.8%(0.55배, 반토막)**. 절대 순서도 뒤집혔다 — 2025-08엔 jest가 vitest의 2.25배였는데 2026-08엔 **vitest가 jest의 1.90배**다. 12개월 만의 완전한 역전이고 [State of JS 2025](https://2025.stateofjs.com/en-US/libraries/)의 "Vitest·Playwright 각각 전년 대비 +14%p"와도 방향이 맞는다. `cypress`는 6.8% → 3.1%로 반토막, `playwright`는 20.8% → 31.1%.

**문제는 안쪽 껍질이다.** `@vitest/browser`는 typescript 대비 1.43% → 3.63%(2.54배)로 잘 자란 듯 보이지만, **Vitest 설치 대비 점유율은 9.4% → 10.2%로 거의 제자리**다. 즉 Browser Mode의 성장은 대부분 **Vitest 자신의 성장에 실려 온 것**이지 jsdom 사용자의 전환이 아니다. 방증도 일관된다 — `jsdom`은 죽지 않았다(typescript 대비 36.2% → 36.6%, **완전 횡보**). `@testing-library/react`도 react 대비 35.1% → 32.8%로 거의 안 줄었고, 대체재로 권장되는 `vitest-browser-react`는 **RTL의 2.3%**다. 정리하면 **"Vitest가 Jest를 대체했다"는 완료된 사실, "실브라우저 컴포넌트 테스트가 jsdom을 대체한다"는 아직 소수 실천**이다. 후자를 이미 일어난 일처럼 쓰는 2026년 블로그들은 과장이다.

**지금 알아둬야 할 이유 한 줄.** 우리 레포는 vitest 설정 **13개가 전부 `environment: 'jsdom'`**이고 Playwright는 이미 물려 있다 — 즉 **두 도구를 다 가졌는데 그 사이를 잇는 층만 비어 있다.** 다음 표준형은 "레이아웃·가시성·포인터가 걸린 컴포넌트만 Browser Mode로 올리고 순수 로직은 jsdom에 남기는 2단 구성"이니, 지금은 신규 테스트 파일 몇 개로 그 경계선을 손에 익혀두면 충분하다.

> 검토했다가 뺀 것 — **TC39 Signals**: 프레임워크 저자 연합이라는 서사가 크지만 [여전히 Stage 1](https://github.com/tc39/proposal-signals), 네이티브까지 최소 2~3년. **Svelte/Solid**: 만족도(State of JS DX 1위)와 채택이 어긋난다 — `svelte`는 react 대비 5.5% → 3.4%로 **정규화 기준 오히려 후퇴**, `solid-js`는 2.1%. **Bun**: 존재감은 확실하지만 npm 다운로드로 런타임 채택을 못 재서 이 브리핑의 측정 규율로는 정직하게 다룰 수 없다 — 보류.

## 오늘의 학습 추천

### Vitest Browser Mode — jsdom과 E2E 사이의 빈 층을 메우는 2단 테스트 구성

([Vitest 4 발표](https://voidzero.dev/posts/announcing-vitest-4) → [Browser Mode 가이드](https://vitest.dev/guide/browser/) → [vitest-browser-react](https://vitest.dev/api/browser/react))

**왜 지금.** 세 가지가 동시에 맞아떨어진다.

1. **우리에게 이미 재료가 다 있다.** vitest 4.1.10, `@playwright/test` 1.62.1, 그리고 vitest 설정 13개가 **전부 jsdom**이다. Browser Mode는 새 도구를 사는 게 아니라 **이미 있는 둘을 잇는 설정**이다.
2. **v5 RC가 rc.2까지 왔다.** vitest 메이저 업그레이드가 곧 온다는 뜻이고, 설정 13개를 한 번에 건드릴 작업이 예정돼 있다면 **그때 테스트 전략도 같이 정리하는 게 두 번 안 건드리는 길**이다.
3. **역전이 데이터로 확인됐다.** Jest→Vitest는 정규화 기준으로 이미 뒤집혔다(vitest가 jest의 1.90배). 다음 질문은 "Vitest를 쓸까"가 아니라 "Vitest 안에서 어디까지 실브라우저로 올릴까"다.

**단, 과장은 걷어내고 시작한다.** 위 레이더에 적었듯 jsdom은 횡보 중이고 RTL도 거의 안 줄었다. **목표는 전면 이관이 아니라 경계선 긋기**다 — jsdom이 구조적으로 답할 수 없는 질문(요소가 실제로 보이는가, 위치·크기가 얼마인가, 스크롤/hover/포인터가 어떻게 동작하는가)만 올리고 나머지는 두는 것.

**시작점 (3단계, 반나절짜리)**
1. [Browser Mode 가이드](https://vitest.dev/guide/browser/)를 읽고 **개인 프로젝트나 패키지 하나**에 `browser.enabled` 프로젝트를 **기존 jsdom 프로젝트와 나란히** 추가한다(교체가 아니라 병렬 — `test.projects`). 한쪽만 켜는 게 아니라 둘이 공존하는 형태를 먼저 만들어 본다.
2. **jsdom에서 지금 모킹으로 때우고 있는 테스트 하나**를 골라 Browser Mode로 옮긴다. `IntersectionObserver` 모킹이나 `getBoundingClientRect` 스텁이 있는 파일이 최적 후보다 — 그 모킹이 통째로 사라지는 걸 눈으로 본다.
3. locator 자동 재시도 모델을 익힌다 — `waitFor`/`act()`로 감싸던 코드가 왜 필요 없어지는지, 그리고 **언제 여전히 필요한지**.

**셀프체크**
1. jsdom에서 `getBoundingClientRect()`가 전부 0을 반환하는 건 버그가 아니라 설계다. 왜 그런가? 그리고 그 사실이 **어떤 종류의 테스트를 구조적으로 불가능하게** 만드는가?
2. Browser Mode와 Playwright E2E는 둘 다 진짜 브라우저를 쓴다. 그런데도 **격리 수준과 실행 속도가 다른 이유**는 무엇인가? 어떤 테스트가 어느 쪽에 속하는가?
3. `@testing-library/react`의 `waitFor`와 Browser Mode locator의 자동 재시도는 무엇이 다른가? 후자가 없애 주는 flakiness의 원인은 정확히 무엇인가?
4. 우리 레포에서 지금 **"E2E로 밀어냈지만 사실 컴포넌트 단위로 검증하면 충분했던"** 테스트를 하나 짚을 수 있는가?
