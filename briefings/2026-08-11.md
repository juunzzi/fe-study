# FE/AI 브리핑 — 2026-08-11

## TL;DR

- **코어 스택은 조용한 한 주.** React·TypeScript·TanStack Query·TC39 모두 8/6 이후 새 릴리스 0건. Next.js도 16.3.1은 canary만 돌고 있다(정식 stable은 여전히 8/3의 16.3.0).
- 대신 Next.js가 **Instant Navigations 실전 적용기**를 냈다 — 자사 v0를 전환하며 `@next/playwright`의 `instant()`로 "즉시성"을 회귀 테스트로 고정한 케이스.
- 우리와 직결되는 릴리스는 **Vite 8.2.1**(우리 8.1.0) — lightningcss minify CSS 버그, `sharedPlugins` chunkImportMap 수정.
- AI: **Claude Code 자체 호스팅 환경 퍼블릭 베타**, Claude API에 **세션 예산 상한·advisor** 추가. v2.1.225는 헤드리스 OAuth 토큰이 덮어써지던 버그를 고쳤다(봇 운영 직결).
- 국내가 풍년 — 토스 **모노리포 catalog 도입기**(우리 pnpm catalog와 같은 문제), 네이버 D2 **Claude Code Skills 토큰 6,900 → 170** 실측.

## 스택 업데이트

### Vite 8.1.0 → 8.2.1 ([릴리스](https://github.com/vitejs/vite/releases/tag/v8.2.1), 2026-08-06)
- lightningcss visitor가 minify 도중 재실행되던 CSS 버그 수정, `sharedPlugins: true`에서 client chunkImportMap 호환 수정, `port: 0` 랜덤 포트, lib entry 해석 시 유저 config를 변형하던 문제 수정.
- 우리 레포 영향: 패치 릴리스라 breaking 없음. CSS minify 결과가 어긋나는 류의 증상을 겪고 있었다면 바로 올릴 값어치가 있다.

### Next.js 16.2.10 → (16.3.0 stable 유지)
- 이 기간 나온 건 **15.5.23**(8/7, 15.x 유지보수 — ReplyServer traversal guard 백포트)뿐이라 우리와 무관.
- 16.3.1은 canary 6개(8/7~8/10)만 나왔다. 아직 정식 없음. 16.2.10 → 16.3 업그레이드 판단은 지난 브리핑 그대로 유효.

### React / TypeScript / TanStack Query / TC39 — 특이사항 없음
- React 최신은 19.2.8(7/21, 우리 19.2.7), TypeScript는 6.0.3 / 7.0.2 그대로, TanStack Query 마지막 릴리스 8/1.
- TC39는 8월 미팅 자체가 없다. 다음은 **미팅 #116, 9/29~10/1 도쿄**. 직전 stage 변동(Await Dictionary → stage 3 등)은 7월분.
- 참고로 TanStack **Form v2 alpha**(8/6)와 **Table v9 정식**(8/4)이 나왔다 — 우리가 쓰진 않지만 Form v2의 `when` 조건부 검증 파이프라인 설계는 볼 만하다. ([Form v2](https://tanstack.com/blog/announcing-tanstack-form-v2-alpha))

## 오늘의 학습 추천

**에이전트에게 지식을 "주입"하지 말고 "고르게" 하기 — Claude Code Skills 컨텍스트 설계**
([네이버 D2 2편](https://d2.naver.com/helloworld/7337586) → [Anthropic Skills 문서](https://code.claude.com/docs/en/skills) → 보조로 [Vercel Skill packs](https://vercel.com/changelog/skill-packs-are-now-available), [라인 AIDD 워크숍](https://techblog.lycorp.co.jp/ko/conditions-for-organizational-aidd-adoption))

- **왜 지금**: 코어 스택이 조용한 주라 억지로 채우기보다, 지금 실제로 값이 움직이는 축을 보는 게 낫다. D2가 낸 6,900토큰 → 170토큰은 감이 아니라 **실측**이고, 결론이 "훅으로 전부 밀어넣지 말고 에이전트가 필요한 것만 열게 하라"는 구조적 원칙이다. 같은 주에 Claude API가 `.claude/skills` 자동 발견을, Vercel이 skill pack 배포를 내놓은 것도 이 축이 표준화되는 신호. 라인 글의 "병목은 툴이 아니라 맥락"이 같은 이야기를 조직 관점에서 반복한다.
- **실코드 연결**: juunzzi-bot의 `skills/<도구>/SKILL.md` + `src/mcp/registry.ts` 구조가 정확히 이 설계를 이미 하고 있다 — CLAUDE.md에 "게이트가 꺼져 있으면 스킬 안내도 함께 뺀다"고 적힌 이유를 D2 글의 토큰 실측과 겹쳐 읽으면, 그 규칙이 왜 비용·품질 양쪽 문제인지가 선명해진다. 실무 레포의 `.claude/skills`도 같은 잣대로 재볼 수 있다.
- **셀프체크**: ① 훅 강제 주입과 에이전트 선택 로딩의 품질 차이가 왜 토큰 수와 같은 방향으로 움직이나? ② 우리 SKILL.md 중 "항상 읽히는" 것과 "필요할 때 열리는" 것의 경계가 지금 어디인가? ③ Vercel skill pack 방식으로 팀 표준 스킬셋을 배포한다면 무엇이 팩에 들어가야 하나?

## 학습 필요 항목 (사용자 추가)

**node:sqlite — Node.js 내장 SQLite 모듈** ([공식 문서](https://nodejs.org/api/sqlite.html))

- **왜 지금**: juunzzi-bot 의 내구 잡 큐가 SQLite 위에 서 있다. 잡이 유실되는지, 재시작 후 어디부터 다시 도는지, 동시 접근이 어떻게 직렬화되는지는 전부 이 계층의 동작이라 큐를 운영하려면 먼저 알아야 한다. `better-sqlite3` 같은 네이티브 드라이버 없이 표준 API 로 갈 수 있는지 판단하는 근거도 여기서 나온다.
- **볼 것**: `DatabaseSync`/`StatementSync` 동기 실행 모델(왜 async 가 아닌지), 트랜잭션 경계와 WAL 모드, prepared statement 재사용, `node:sqlite` 의 안정성 등급과 Node LTS 별 가용 여부.
- **셀프체크**: ① 동기 API 가 이벤트 루프를 막는데도 괜찮은(혹은 안 괜찮은) 조건은 무엇인가? ② 잡 큐에서 "정확히 한 번 꺼내기"를 SQLite 트랜잭션으로 어떻게 보장하나? ③ 프로세스가 잡 처리 중 죽으면 그 잡은 어떤 상태로 남고, 누가 되살리나?
