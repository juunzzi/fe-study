## 지금 알아둘 개념 (FE)

### Suspense 경계는 렌더 최적화가 아니라 **스트리밍 단위**다

각 Suspense 경계는 독립된 스트리밍 단위라서, **DOM 순서가 아니라 데이터가 도착한 순서로** 해소된다. 페이지 아래쪽의 빠른 쿼리가 위쪽 느린 쿼리보다 먼저 그려질 수 있다. 서버는 shell 을 즉시 흘려보내고 느린 조각만 나중에 채운다 — 그래서 TBT·INP 같은 체감 지표가 움직인다.
([SitePoint 스트리밍 성능 가이드](https://www.sitepoint.com/react-server-components-streaming-performance-2026/), [jsmanifest — RSC 패턴과 함정](https://jsmanifest.com/react-server-components-patterns-pitfalls-2026))

**연결해서 읽을 것**: 8/11 브리핑에 정리한 [v0 Instant Navigations 적용기](https://nextjs.org/blog/making-v0-navigations-instant)의 수정 패턴이 "동적 데이터 접근을 Suspense 경계 아래로 내리고 나머지를 shell 에 포함시키기" 하나로 수렴한다. 즉 Instant Navigations 를 켜는 일은 옵션 플래그 문제가 아니라 **경계를 어디에 긋느냐**의 문제다. 우리 앱에서 loading.tsx 가 없는 라우트를 찾는 것과 같은 작업이다.

**셀프체크**: ① 경계 하나를 위로 올리면 무엇이 빨라지고 무엇이 느려지나? ② shell 에 들어가면 안 되는 것(= 요청마다 달라지는 값)은 무엇인가? ③ 경계가 너무 잘게 쪼개지면 생기는 비용은?

### `node:sqlite` — 실험 딱지를 떼는 중

Node 내장 SQLite 가 **Stability 1.2 (release candidate)** 로 올라왔다(v25.7.0). 핵심 성질은 **동기**다 — `DatabaseSync`·`StatementSync` 의 `run/get/all/iterate` 가 전부 블로킹이고, 유일한 async 는 `backup()` 이다. 그 외에 세션/changeset 으로 변경분을 떠서 다른 DB 에 적용하는 API 가 있고, `defensive` 옵션은 v25.5.0 부터 기본 true 다.
([공식 문서](https://nodejs.org/api/sqlite.html))

## 신규 모델 — 오픈웨이트 지형

숫자 하나로 줄 세우지 말고 **무슨 축에 베팅한 모델인가**로 읽는 게 실용적이다.

- **GLM-5.2** (Z.ai, 6/13 공개 · 6/17 MIT 웨이트) — ~750B MoE, 활성 ~40B, 1M 컨텍스트. Terminal-Bench 2.1 **81.0**(Claude Opus 4.8 85.0), SWE-bench Pro 62.1 로 GPT-5.5(58.6) 상회. **장문맥 에이전틱 코딩** 축. ([VentureBeat](https://venturebeat.com/technology/z-ais-open-weights-glm-5-2-beats-gpt-5-5-on-multiple-long-horizon-coding-benchmarks-for-1-6th-the-cost))
- **DeepSeek V4 (Flash)** — 공개 API 단가 최저선을 계속 끌어내리는 **가격** 축.
- **Kimi K3** (Moonshot) — 2.8T 파라미터로 소개된 **규모** 축.
- **MiniMax M3** — 텍스트·이미지·영상까지 보는 **멀티모달** 축.
- **Inkling** (Thinking Machines Lab, 7월) — 975B total / ~41B active. MoE 로 비용을 누르는 설계.
- **Qwen3-Coder-Next** — 로컬에서 굴리는 **온디바이스 코딩** 축.

([비교 정리 A](https://kingy.ai/news/best-open-weight-ai-models-in-2026-glm-5-2-vs-deepseek-v4-vs-kimi-k2-6-vs-qwen-vs-mistral/), [비교 정리 B](https://cline.ghost.io/best-open-weight-models-that-matter-in-2026/))

⚠️ **숫자는 2차 출처마다 어긋난다** — GLM-5.2 파라미터가 744B / 753B 로 갈리는 식이다. 인용할 일이 있으면 모델 카드나 공식 발표를 직접 확인할 것. 벤치 점수도 같은 이름의 벤치가 버전(2.1 등)마다 다르다.

## 신규 AI 오픈소스

- **OpenClaw** — 2026 년 오픈소스 판에서 가장 시끄러웠던 프로젝트. 셀프호스트로 도는 자율 에이전트이고, **메신저(WhatsApp·Slack·Telegram 등)를 주 UI 로 쓰는** 게 특징이다. 스타 수는 출처마다 302K~355K 로 다르게 적히는데(성장 속도 자체가 논점), 어느 쪽이든 React 가 8년 걸린 지점을 훨씬 빠르게 통과했다. ([Wikipedia](https://en.wikipedia.org/wiki/OpenClaw))
- **에이전트 프레임워크 지형** — 상태 있는 프로덕션 에이전트는 **LangGraph**, 멀티에이전트 역할 분담은 **CrewAI**·**AutoGen**·**MetaGPT**, 벤더 진영은 **Google ADK**·**Microsoft Agent Framework**(Semantic Kernel 흡수), TypeScript 쪽은 **Mastra**, 최소주의는 **smolagents**. ([Firecrawl 비교](https://www.firecrawl.dev/blog/best-open-source-agent-frameworks))

**왜 우리에게 중요한가**: juunzzi-bot 은 이 프레임워크들을 쓰지 않고 SQLite 내구 잡 큐 + Socket Mode 복원력 + 프로파일 기반 도구 경계를 직접 짠 하네스다. 남이 만든 그래프 런타임을 안 쓰기로 한 선택이 무엇을 얻고 무엇을 포기한 것인지 — 상태 지속성, 재시작 복구, 도구 권한 경계 세 축에서 비교해 보면 우리 설계를 남에게 설명할 수 있게 된다.

## 오늘의 학습 추천

**`node:sqlite` — 드라이버 없이 내장 SQLite 로 잡 큐를 세우는 법** ([공식 문서](https://nodejs.org/api/sqlite.html))

- **왜 지금**: juunzzi-bot 의 내구 잡 큐가 SQLite 위에 서 있다. 잡이 유실되는지, 재시작 후 어디부터 다시 도는지, 동시 접근이 어떻게 직렬화되는지는 전부 이 계층의 성질이라 큐를 운영하려면 먼저 알아야 한다. RC 로 올라온 지금이 `better-sqlite3` 같은 네이티브 드라이버를 계속 쓸지 판단할 시점이기도 하다.
- **볼 것**: 동기 실행 모델(왜 async 가 아닌지), `BEGIN`/`COMMIT` 으로 여는 트랜잭션과 `isTransaction`, WAL 저널 모드(`PRAGMA journal_mode = WAL`)와 `timeout`(busy timeout), prepared statement 재사용, session/changeset, `defensive` 기본값.
- **실코드 연결**: juunzzi-bot 의 `jobStore` — 잡을 꺼내면서 상태를 바꾸는 부분이 트랜잭션으로 감싸여 있는지, `recoverInflight` 가 재시작 때 무엇을 근거로 되살리는지 읽어 본다.
- **셀프체크**: ① 동기 API 가 이벤트 루프를 막는데도 괜찮은(혹은 안 괜찮은) 조건은? ② "정확히 한 번 꺼내기"를 SQLite 트랜잭션으로 어떻게 보장하나? ③ 프로세스가 잡 처리 중 죽으면 그 잡은 어떤 상태로 남고 누가 되살리나? ④ WAL 을 켜면 동시성이 어떻게 달라지나?
