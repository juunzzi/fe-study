## TL;DR

- **Next.js stable 은 16.3.1 그대로.** 대신 canary 에 볼 게 둘 — `AsyncLocalStorage` 를 global symbol 에 앵커해 **모듈 이중 평가 크래시**를 막은 [#97255](https://github.com/vercel/next.js/pull/97255), 그리고 acdlite 가 직접 올린 **`concurrentRouterQueue` 스캐폴딩**([#97413](https://github.com/vercel/next.js/pull/97413)). 라우터를 React concurrent 모델에 맞춰 다시 쓰기 시작했다는 신호다.
- **pnpm 12.0.0-rc.6 (8/15) 이 이번 창 최대 건**이고 우리에게 직접 걸린다 — `pnpm add yarn` 의 의미가 바뀌는 breaking 이 있고, 11.22.0 은 catalog 옵션을 리네임했다(`cleanupUnusedCatalogs` → `catalogPrune`). 우리는 catalog 를 전면적으로 쓴다.
- **React·TanStack Query·TC39 는 창 안 실질 변화 0.** TC39 는 8월 미팅 자체가 없다(격월, 다음은 9/29~10/1 도쿄).
- **오픈웨이트 지형이 "체급별로 라이선스를 가르기" 시작했다** — 27B 는 Apache-2.0, 2.4T 는 커스텀 + MaaS 매출 조항. 그리고 **증류 파생은 교사 모델 라이선스를 태그에 안 보여준다.**
- 오늘의 학습 추천은 **Cache Components (`'use cache'`)** — 우리는 Next 16.3 을 쓰면서 이 플래그를 **안 켠 상태**다. Next 16 의 간판 기능을 켤지 말지 판단하려면 캐시 키가 무엇으로 만들어지는지부터 알아야 한다.

## 스택 업데이트

### Next.js — 16.3.2 없음(확인함). canary 에 둘

stable 은 **16.3.1(8/13)** 그대로다. 창 안 canary 는 `.20`(8/15)·`.21`(8/16) 둘이고 주목할 머지가 둘 있다.

**① [#97255](https://github.com/vercel/next.js/pull/97255) — 6개의 AsyncLocalStorage 를 global symbol 에 앵커** (8/16). Next 는 요청 컨텍스트를 `workAsyncStorage`·`workUnitAsyncStorage` 같은 ALS 인스턴스로 나른다. 이것들은 realm 안에서 **싱글턴이어야** 하는데, Node 의 `fs` 가 심볼릭 링크를 해소하지 않은 경로를 돌려주면 모듈 로더가 그 경로를 캐시 키로 써서 **같은 모듈이 두 번 평가**된다(pnpm 설치에서 `next/dist/...` 가 두 벌이 되는 그 모양이다). 인스턴스가 갈라지면 `dev` + Cache Components 조합에서 치명적 크래시가 났다. 고친 방식이 배울 만하다 — 각 storage 를 **global symbol 에 묶고, 키에 Next 버전을 넣어** 호환 안 되는 store 가 공유되는 것까지 막는다. worker thread·edge sandbox 는 `globalThis` 가 따로라 자기 storage 를 유지한다.

**② [#97413](https://github.com/vercel/next.js/pull/97413) — `concurrentRouterQueue` 플래그 스캐폴딩** (8/16, acdlite). 클라이언트 라우터 큐 재작성의 토대다. 모듈을 `concurrent-router-queue.ts`(신규) / `sequential-router-queue.ts`(기존)로 갈라 플래그가 꺼지면 트리셰이킹되게 했고, **지금은 켜면 모든 라우터 동작이 throw 하는 placeholder** 다. 목표는 라우터를 React concurrent rendering 모델에 맞추는 것. **8/15 회차에서 다룬 `enableParallelTransitions` 와 같은 줄기**다 — React 팀이 "언제 커밋하는가"를 손보면서 라우터도 같이 끌고 가고 있다.

그 밖: [#97321](https://github.com/vercel/next.js/pull/97321) hydration 전 back 복구를 브라우저에서 대기(gaearon), [#97402](https://github.com/vercel/next.js/pull/97402) 클라이언트 라우터 모듈 재구성, [#97388](https://github.com/vercel/next.js/pull/97388) metadata resolution primitive 추출.

**우리 영향**: 우리는 **16.3.0** 이다. 8/15 회차에서 권고한 **16.3.1 업그레이드는 그대로 유효**하고(순수 fix, breaking 없음), 위 두 건은 아직 canary 라 지금 볼 건 아니다. 다만 #97255 는 **Cache Components 를 켜려 할 때 dev 에서 밟는 종류**라, 아래 학습 추천을 실제로 실험한다면 16.3.2 가 나온 뒤에 하는 게 낫다.

**우리 영향**: 여전히 6.0.3(4/16, 6.x 최종본) 고정. 지금 깨지는 건 없지만 **유지보수가 끝난 라인**이라는 상태는 그대로다. 지난 회차의 액션 하나(릴리스 모니터링 소스를 `microsoft/typescript-go` 로 교체)가 아직 유효하다.

## 지금 알아둘 개념

### ① AsyncLocalStorage — `cookies()` 가 프롭 없이 흐르는 원리, 그리고 그 싱글턴이 깨지는 자리

**무엇인가.** 서버 컴포넌트에서 `await cookies()` 를 부르면 **어떤 요청의 쿠키인지 아무도 안 넘겨줬는데** 맞는 값이 나온다. 이게 마법이 아니라 `node:async_hooks` 의 **`AsyncLocalStorage`(ALS)** 다. 개념은 "비동기 호출 체인을 따라 자동으로 따라다니는 변수"다.

```js
const als = new AsyncLocalStorage()
als.run({ reqId: 'a1' }, () => {
  setTimeout(() => als.getStore())   // { reqId: 'a1' } — 인자로 안 넘겼는데도
})
als.getStore()                        // undefined — run 밖은 아무것도 없다
```

`run(store, cb)` 로 연 스코프 안에서 시작된 **모든 비동기 작업**(Promise, `setTimeout`, I/O 콜백)이 그 store 를 상속한다. Node 에서 `AsyncLocalStorage`·`run`·`getStore`·`bind`·`snapshot` 은 **Stability 2 (Stable)** 이고, `enterWith`·`exit`·`disable`·`withScope` 는 아직 **실험적**이다.

**핵심 함정 셋** (문서가 직접 경고하는 것):
- **콜백 기반 API 는 컨텍스트를 잃는다.** 콜백을 큐에 저장해 뒀다가 나중에 부르는 라이브러리 안에서는 `getStore()` 가 `undefined` 다. 해법은 `util.promisify` 로 감싸거나 `AsyncLocalStorage.snapshot()` / `bind(fn)` 으로 **컨텍스트를 함수에 박아 두는 것**이다.
- **`enterWith` 는 스코프가 없다.** `run` 과 달리 현재 동기 실행 전체와 그 이후로 번지고, 이벤트 핸들러 전체에 영향을 준다. 편해 보여서 손이 가는데 그게 함정이다.
- **`withScope`(v25.9+, 실험적)는 `using` 과 짝이다.** 지난 회차에서 다룬 Explicit Resource Management 가 여기서 다시 나온다 — `using _ = als.withScope(store)` 로 스코프를 열면 블록 끝에서 이전 값이 자동 복원된다. 단 **첫 `await` 이전에 쓰면 호출자 컨텍스트까지 오염된다**고 문서가 못박는다. async 함수에는 `run` 을 쓰라는 것.

**왜 지금.** ① 오늘 나온 Next [#97255](https://github.com/vercel/next.js/pull/97255) 가 정확히 이 층의 버그다. Next 는 요청 상태를 **6개의 ALS 인스턴스**로 나르는데, 심볼릭 링크가 해소되지 않아 `next/dist/...` 가 두 번 평가되면 **인스턴스가 두 벌이 되고 `getStore()` 가 남의(혹은 빈) store 를 본다.** 고친 방식이 교훈이다 — 모듈 스코프 싱글턴은 **모듈이 한 번만 평가된다는 가정 위에 서 있고, pnpm·심볼릭 링크·모노레포에서 그 가정이 깨진다.** 그래서 **global symbol** 로 올리고 키에 버전을 박았다. ② 이건 프레임워크만의 문제가 아니다. `React.cache`, Datadog·OpenTelemetry 의 트레이스 전파, 요청 스코프 DB 트랜잭션 — **"컨텍스트가 안 따라온다"** 는 증상은 전부 이 이름으로 검색해야 나온다. ③ 표준화도 진행 중이다: TC39 **[AsyncContext](https://github.com/tc39/proposal-async-context) 가 Stage 2** 이고 `AsyncContext.Variable` / `AsyncContext.Snapshot` 형태다. 언젠가 브라우저에서도 같은 개념을 쓰게 된다.

**실코드 연결 (juunzzi-bot).** 잘 맞는 자리가 셋이다. ① **슬랙 스레드 좌표**(채널·thread_ts·요청자)를 지금 함수 인자로 계속 내려주고 있다면, 그게 정확히 ALS 가 없애는 프롭 드릴링이다. ② **잡 큐** — 잡 하나가 시작될 때 `als.run({ jobId, dedupKey }, ...)` 로 감싸면 로그·에러 리포트가 자동으로 그 잡을 알게 된다. 지금은 로그마다 id 를 손으로 붙이고 있을 것이다. ③ **`setTimeout`·`createTicker` 를 건너는 자리** — 여기가 컨텍스트가 끊기는지 이어지는지 실제로 확인해 볼 값어치가 있다(타이머는 이어지고, 큐에 저장했다 나중에 부르는 콜백은 끊긴다).

**셀프체크**
① `als.run()` 안에서 던진 Promise 를 **밖에서** `await` 하면 그 continuation 은 store 를 보는가?
② `getStore()` 가 `undefined` 인 버그를 만났을 때, 원인이 "컨텍스트 손실"인지 "인스턴스 이중화"인지 어떻게 구분하는가? (#97255 가 후자다)
③ `snapshot()` 과 `bind(fn)` 은 무엇이 다른가? 이벤트 에미터에 리스너를 등록할 때 어느 쪽을 쓰는가?
④ ALS store 에 큰 객체를 넣으면 언제 GC 되는가? 요청이 끝났는데도 안 죽는 경우는 어떤 모양인가?

([Node 문서](https://nodejs.org/api/async_context.html) · [TC39 AsyncContext](https://github.com/tc39/proposal-async-context))

### ② `'use cache'` — 캐시 키가 **무엇으로** 만들어지는지 모르면 켜면 안 된다

**무엇인가.** Next 16 의 간판 기능인 **Cache Components**(`cacheComponents: true`)를 켜면 쓸 수 있는 지시어다. 라우트·컴포넌트·함수 앞에 `'use cache'` 를 붙이면 반환값이 캐시된다(전부 `async` 여야 한다). 전부인 것 같지만, **실제로 알아야 하는 건 캐시 키의 구성**이다:

1. **Build ID** — 빌드마다 바뀐다. 즉 **배포하면 캐시가 통째로 날아간다**(`deploymentId` 를 설정하면 그게 대신 쓰인다).
2. **Function ID** — 코드 상 위치와 시그니처의 해시.
3. **직렬화된 인자** — 컴포넌트면 props, 함수면 인자.
4. dev 전용 **HMR refresh hash**.

여기서 대부분이 놓치는 한 줄: **"캐시된 함수가 바깥 스코프의 변수를 참조하면 그 변수가 자동으로 캡처돼 인자로 바인딩되고, 캐시 키의 일부가 된다."** 클로저로 `userId` 를 읽으면 **유저마다 별개의 캐시 엔트리**가 생긴다는 뜻이다 — 코드에는 아무것도 안 적혀 있는데.

**제약이 곧 설계다.**
- **`cookies()`·`headers()`·`searchParams` 를 캐시 스코프 안에서 못 읽는다.** 그리고 **호출 스택을 따라간다** — 캐시된 함수가 부른 헬퍼가 읽어도 같은 에러(`next-request-in-use-cache`)다. 더 고약한 건 타이밍이다: 동적 렌더 라우트에서는 **`next build` 는 통과하고 `next start` 에서 터진다.**
- **인자와 반환값의 직렬화 규칙이 다르다.** 인자는 Server Component 직렬화(더 엄격), 반환값은 Client Component 직렬화. 그래서 **JSX 를 반환할 수는 있어도 인자로 받을 수는 없다**(패스스루 제외). 클래스 인스턴스·함수·Symbol·`URL` 은 불가.
- **패스스루가 탈출구다.** `children` 이나 Server Action 을 **들여다보지 않고 그대로 넘기기만 하면** 캐시 엔트리에 영향을 주지 않는다. 캐시된 껍데기 안에 동적인 자식을 끼우는 조합이 여기서 나온다.
- **`React.cache` 는 경계 안에서 격리된다.** 바깥에서 `cache()` 로 넣은 값이 안에서 안 보인다. 데이터를 넣는 길은 **인자뿐**이다.
- **빌드가 멈추면(50초 타임아웃) 원인은 하나다** — 캐시 경계 밖에서 만들어진 "런타임에만 resolve 되는 Promise" 를 안에서 `await` 한 것. props 로 넘겼든, 클로저로 잡았든, 공유 `Map` 에서 꺼냈든.
- 수명은 `cacheLife` 다. 안 쓰면 default 프로파일(stale 5분/revalidate 15분/만료 없음)이 적용되고, **짧은 수명 캐시를 명시적 `cacheLife` 가 없는 캐시 안에 중첩하면 프리렌더에서 빌드가 실패한다.** 무효화는 `cacheTag` + `revalidateTag`/`updateTag`. 클라이언트 라우터는 설정과 무관하게 **최소 30초 stale** 을 강제하고, 서버는 `x-nextjs-stale-time` 헤더로 그걸 맞춘다.

**왜 지금.** ① 우리는 Next **16.3** 을 쓰면서 `cacheComponents` 를 **안 켰다**. 즉 이 프레임워크의 간판 기능을 **판단 보류 상태**로 두고 있는데, 판단하려면 위 목록을 알아야 한다. ② 8/13 회차에서 다룬 `<Activity>` 의 "Next 16 이 클라이언트 내비게이션에서 이전 라우트를 언마운트하지 않는다"도 **`cacheComponents: true` 조건부**였다. 즉 이 플래그 하나가 캐싱만이 아니라 **라우팅 생명주기까지 바꾼다.** ③ 오늘 나온 #97255 크래시도 `dev` + Cache Components 조합에서 났다. **켜는 순간 밟는 지형이 실재하고, 지금 활발히 움직인다.**

**실코드 연결.** 우리 앱에서 지금 확인할 것 셋: ① 서버 컴포넌트 중 **요청과 무관한 데이터**(공통 코드값, 정적 목록, 외부 API 의 느린 조회)를 매 요청 가져오는 자리 — 여기가 첫 후보다. ② 그 컴포넌트들이 **호출 스택 어딘가에서 `headers()`/`cookies()` 를 읽는지** — 읽는다면 그 값을 인자로 끌어올리는 리팩터가 선행돼야 한다. ③ 서버 데이터를 감싸 넘기는 **클래스 인스턴스·`URL` 객체**가 props 에 섞여 있는지 — 있으면 직렬화에서 막힌다.

**셀프체크**
① 캐시된 컴포넌트가 클로저로 `userId` 를 읽으면 캐시 엔트리는 몇 개가 되는가? 그게 의도한 것인가, 사고인가?
② `next build` 는 통과하는데 `next start` 에서만 터지는 캐시 에러는 왜 그런 타이밍을 갖는가?
③ 로그인 사용자별로 다른 화면을 **캐시하면서** 개인정보를 안 새게 하려면 경계를 어디에 그어야 하는가? (패스스루와 `use cache: private` 이 각각 무엇을 푸는지)
④ 배포할 때마다 캐시가 전부 날아가는 게 기본값인데, 그걸 원치 않으면 무엇을 설정하는가? 그때 새로 생기는 위험은?

## 모델·오픈소스 지형

숫자는 HuggingFace API·`config.json`·LICENSE 원문에서 직접 확인했고, 못 한 건 **미확인**으로 적었다. 이번 열흘의 축은 둘이다 — **체급이 라이선스를 가르기 시작했다**, 그리고 **가치가 모델에서 하네스의 라우팅 레이어로 옮겨갔다.**

**축 1 — 프론티어 체급, 그리고 라이선스 계층화.**
**[Qwen/Qwen3.8-2.4T-A95B](https://huggingface.co/Qwen/Qwen3.8-2.4T-A95B)** (8/8 공개, lastMod 8/12). config 직접 확인 — **2.4T total / 95B active**, 512 experts 중 routed 10 + shared 1, 92 layers, GQA 64/4, **`max_position_embeddings` = 262,144**. 카드는 "1,010,000 토큰까지 확장 가능"이라 하지만 **네이티브는 262K** 이고 확장 방식은 미확인이다.
읽을 지점은 스펙이 아니라 **라이선스가 `apache-2.0` 이 아니라 커스텀 `qwen3.8-max`** 라는 것. 같은 세대의 27B 는 Apache-2.0 인데 프론티어만 갈랐다. LICENSE 원문을 직접 읽어 확인한 조건: 상업 사용·재배포·파인튜닝·파생 **허용**, MAU 1억 또는 월매출 $20M 초과 제품은 **UI 에 모델명 표기 의무**, 그리고 **MaaS 또는 "AI Work Assistant" 사업으로 12개월 누적 매출 $50M 초과 시 별도 라이선스 취득 의무**. 지역 제한(한국·EU 제외) **없음**, 금지용도 목록 **없음**, 증류 금지 **없음**. 마지막 조항이 제품 회사가 실제로 밟을 수 있는 유일한 지점이다.

**축 2 — 라이선스 함정: 증류가 계보를 세탁한다.** 이번 회차에서 가장 실무적인 발견.
**[empero-ai/Qwen3.8-9B](https://huggingface.co/empero-ai/Qwen3.8-9B)** (8/15) 는 frontmatter 가 `license: apache-2.0`, `license_link` 는 opensource.org, `base_model` 은 Apache 인 Qwen3.5-9B 다. **그런데 카드 본문은 "Qwen3.8-2.4T-A95B 를 full-parameter distillation 했다"고 명시한다** — 아키텍처 베이스만 Apache 고 **지식의 출처인 교사 모델은 커스텀 라이선스**다. 다행히 교사 라이선스에 증류 금지가 없어 곧바로 위반은 아니지만, **HF 태그도 `base_model` 필드도 계보를 안 보여준다**는 게 요점이다. 파생 모델 도입 심사는 카드 본문을 읽어야 한다.
같은 창의 대조군: [logic65/Qwen3.8-Whittle-16B](https://huggingface.co/logic65/Qwen3.8-Whittle-16B)(8/16)는 베이스가 실제로 Apache 인 27B-FP8 이라 상속이 맞다. 그리고 **낯선 이름이라고 반려하면 손해인 경우**도 있다 — NVIDIA 의 `openmdw-1.1` 은 원문을 읽어 보니 사실상 퍼미시브다(상업 허용, 카피레프트·지역제한·AUP 없음, 조건은 특허 소송 시 권리 소멸 + 재배포 시 사본 동봉).
조항 **미확인**으로 남긴 것: `IndexTeam/IndexTTS-2.5` 의 `bilibili-model-license`, `RadixArk/Qwen3.8-27B-DSpark` 의 `other`.

**축 3 — 가격·효율: "얼마나 작게"에서 "어느 실리콘에 정확히 맞추는가"로.** 창 안에서 가장 붐빈 축이고, 전부 같은 27B 를 대상으로 한 서로 다른 베팅이다.

범용 GGUF 가 아니라 **하드웨어 SKU 이름이 레포명에 박히기 시작했다.** 로컬 실행을 검토한다면 "이 모델 돌아가나"가 아니라 "내 칩에 맞춘 빌드가 있나"가 질문이 된다.

**축 4 — 로컬·단일 파일 추론의 재유행.** [antirez/h3.c](https://github.com/antirez/h3.c)(8/9, MIT, 2,052★) — MiniMax H3 를 Mac 에서 돌리는 **의존성 없는 C 추론 엔진**. llama2.c 계보를 antirez 가 이어받았다. 같은 축 원류로 `FareedKhan-dev/kimi-k3-in-c`(8/1, 5,838★, 2.78T 를 CPU·8.24GB RAM 에서). 그리고 `Atomic-Germ/LFM2-1.2B-RAG`(8/16)는 GPU 가 아니라 **NPU 를 타깃한 양자화** — 이 방향의 GGUF 가 나오기 시작했다는 신호다.

**축 5 — 멀티모달: "작고 정직한" VLM.** [CohereLabs/North-Micro-Vision-Instruct](https://huggingface.co/CohereLabs/North-Micro-Vision-Instruct)(8/10) — **Apache-2.0, 게이팅 없음**. Cohere Labs 치고 이례적이라 함정을 찾으러 갔는데 **없었다**는 게 뉴스다. 2.4B(LM 2B + vision 400M), 가중치 ~2.48GB, 11개 언어에 **한국어 포함**. 카드가 스스로 한계를 밝힌다 — 언어 백본은 128K 지만 **멀티모달 검증 범위는 8K**, 그리고 "추론 모델이 아니며 수학·코드 생성은 제한적". 프로토타이핑·파인튜닝 베이스 포지션이다. 곁: [sand-ai/MAGI-2-preview](https://huggingface.co/sand-ai/MAGI-2-preview)(8/3, Apache-2.0)는 **오디오·비디오를 후처리로 붙이지 않고 한 모델에서 동기 생성**(파라미터 수는 config 가 비어 미확인).

**축 6 — 하네스의 위성 생태계. 이번 창의 진짜 사건.** 지난 회차의 `deepseek-harness`(공개 이틀 만에 95k★) 자체가 아니라, **그 위에 3일 만에 형성된 플러그인 층**이다. 8/11~8/14 사이 생성된 것만: desktop 클라이언트 8,877★ · awesome 큐레이션 5,094★ · web UI 3,420★ · two-phase 프리셋 3,019★ · **routing-suite 2,809★** · TUI 1,542★. 합쳐 일주일에 별 2만 개다.
읽을 것 둘. ① 하네스를 **커널**로 보고 가치를 플러그인·프리셋 레이어에 두는 베팅이 즉시 성립했다. ② 그중 2,800★ 를 먹은 게 **태스크 인지 추론모드 라우터**라는 점 — 제품의 승부처가 모델 선택이 아니라 **추론모드 배분**으로 옮겨가고 있다. 다만 그 `dsh-routing-suite` 는 **라이선스가 없다(None)** — 사내 도입 불가다.

**축 7 — 규범 쪽 한 건.** `guillaumemeyer/watermarks-remover`(8/11, MIT)가 **6일 만에 11,409★**. 멀티벤더 AI provenance 마크 제거(유니코드 위생 + 통계적 리라이트 + C2PA 메타데이터)다. 지난 회차에서 다룬 Anthropic 워터마크의 **반대편 데이터**로 읽어야 한다 — provenance 표준에 대한 사용자 저항이 이미 규모를 가졌다는 뜻이고, C2PA 를 제품에 넣는 논의가 있다면 이 숫자가 근거의 반대쪽이다.

## 떠오르는 스택 레이더

**먼저, 측정 규율이 이번에 스스로를 증명했다.** 지난 회차의 "npm 절대 다운로드는 못 믿는다"(zod = 5.93배 = 생태계 평균)를 월별로 뜯어보니 2026-03~05 에 레지스트리 전체가 **계단식**으로 뛴다: zod 255.8M(25-12) → 547.5M(26-03) → 1,024.7M(26-07), react 236.1M → 464.1M → 689.3M, typescript 418.3M → 687.0M → 1,045.9M. **React 사용자가 4개월 만에 2배가 될 리 없다.**
잣대가 생각보다 가혹하다는 것도 확인해 둔다 — 정규화하면 **react 0.61 / next 0.57 / @tanstack/react-query 0.81 / typescript 0.45** 로 우리 스택이 전부 1.0 미만이다. 즉 **정규화 1.0 이상이면 이미 메인스트림보다 빨리 크는 중**이고 2.0 이상은 드물다. 주의 하나 더: 단일 월 끝점은 취약하다(`vite` 는 2025-08 이 473M, 09 가 162M 이라 기준월 자체가 이상치 — vite 의 norm 0.23 은 못 믿는다). **추이를 같이 봐야 한다.**

### ① Better Auth — 인증을 SaaS 에서 내 DB 로 되가져오기

**뭐가 다른가.** Clerk·Auth0 는 인증을 외부 서비스로 밀어내고, NextAuth/Auth.js 는 Next 에 붙어 있다. Better Auth 는 **프레임워크 무관 + 세션이 내 DB 에 사는** 라이브러리다. 세션 즉시 무효화가 가능하고, 조직·멀티테넌시·2FA·패스키가 플러그인으로 들어오며 안 쓰는 건 번들에서 빠진다. "인증 = 벤더 계약"을 **"인증 = 내 스키마"** 로 되돌리는 쪽이다.

**성숙도: 주류 진입 초입. 이번 조사에서 신호가 가장 깨끗하다.** 정규화 **4.00배**(raw 23.69x, 1,043,810 → 24,731,690/월), stars **29,562**, 최신 stable **1.6.29(8/14)**, 1.7.0-rc 진행 중. 결정적인 건 **월별 곡선에 계단이 없다**는 점이다 — 1.04→1.36→1.74→2.09→2.81→3.80→4.89→8.01→9.94→13.28→17.65→24.73M 의 매끄러운 지수 성장. 대조군도 일관된다: **next-auth 0.53 / @auth/core 0.73 / @clerk/nextjs 0.75 — 기존 강자 셋 모두 점유율이 빠지는 중**이다.

**지금 알아둘 이유 한 줄.** 앱에 인증을 새로 붙일 일이 생기면 2026년의 기본값은 이미 NextAuth 에서 여기로 넘어갔다 — 나중에 갈아타는 것보다 **지금 데이터 모델을 한 번 읽어두는 비용이 훨씬 싸다.** ([GitHub](https://github.com/better-auth/better-auth))

### ② Standard Schema — 스키마 검증이 "라이브러리"에서 "프로토콜"이 됐다

**뭐가 다른가.** 지금까지는 프레임워크가 zod 를 직접 껴안았다(tRPC v10 처럼). Standard Schema 는 검증 라이브러리들이 공통으로 구현하는 **최소 인터페이스(`~standard` 프로퍼티)** 를 정의해서, 소비하는 쪽이 zod·valibot·arktype 중 무엇이든 받게 만든다. **zod 가 지배자에서 "교체 가능한 구현체"로 강등된 것**이 핵심이다.

**성숙도: 조용히 주류.** 실제로 크는 건 경쟁 검증기가 아니라 **규격 자체**다 — `@standard-schema/spec` 정규화 **2.38배**(26.1M → 367.4M/월), spec v1.1.0(2025-12-15), stars 3,586. `valibot` 은 정규화 **1.62배**(6.87M → 66.0M/월, 1.4.2 / 6-28, stars 8,932)이고 레포가 1인 메인테이너에서 **조직(`open-circle/valibot`)으로 이관**됐다 — 지속성 리스크가 줄었다는 신호다. 반면 **경쟁자들은 오히려 빠진다**: arktype 0.62, typebox 0.34, typia 0.15. 채택처는 TanStack Form·Hono·oRPC.
곁들여 이게 **절대값 함정의 교과서**다 — `@sinclair/typebox` 는 월 465M 으로 valibot(66M)의 **7배**인데 정규화는 **0.34**다. 절대 수만 보면 승자로 보이지만 순수하게 생태계 표류에 실려가는 중이다.

**지금 알아둘 이유 한 줄.** zod 를 계속 써도 되지만 **라이브러리 선택의 무게가 사라졌다는 걸 알아야 한다** — 새 코드에서 `z.infer` 대신 `StandardSchemaV1.InferOutput` 으로 타입을 뽑아두면 나중에 번들 크기 때문에 갈아탈 때 소비자 코드를 안 건드린다. ([GitHub](https://github.com/standard-schema/standard-schema))

### ③ Convex — 서버가 무효화를 밀어주는 리액티브 백엔드 (우리 스택의 정확한 반대편)

**뭐가 다른가.** TanStack Query 는 **클라이언트가 언제 stale 인지 추측하는** 구조다(`staleTime`, `invalidateQueries`, refetch 정책). Convex 는 쿼리가 읽은 데이터를 서버가 추적해서, 그 데이터가 바뀌면 **서버가 구독자에게 밀어준다** — **수동 무효화라는 개념 자체가 없다.** 지난 회차의 sync engine(TanStack DB·Zero)이 "로컬 우선"에 베팅했다면, Convex 는 **DB·함수·구독을 한 덩어리로 소유하는 쪽**에 베팅한다.

**성숙도: 성장.** 정규화 **2.52배**(raw 14.94x, 352,153 → 5,260,219/월), stars **12,386**(convex-backend, 오픈소스), 최신 **1.44.0(8/13)**. 절대량은 아직 작지만 월별 곡선에 계단이 없다(0.35→0.48→0.60→0.70→0.75→1.09→1.36→2.07→2.38→3.08→3.66→5.26M).

**지금 알아둘 이유 한 줄.** `invalidateQueries` 를 어디에 넣을지 매번 고민하고 있다면, **그 고민 자체를 없앤 설계가 어떤 모양인지 한 번 보는 게 남는다** — 갈아타지 않아도 캐시 무효화를 보는 눈이 바뀐다. ([GitHub](https://github.com/get-convex/convex-backend))

**차점**: `@openai/agents` 정규화 **4.48**(221K → 5.87M, stars 3,624, 0.16.1 / 8-16, 곡선 깨끗). "AI SDK 를 프레임워크로 보는 흐름"은 실측으로도 살아 있다. 다만 아직 0.x 라 API 가 흔들린다.

### 과대평가 깎기 — 이번 회차에서 가장 쓸모 있는 네 문단

**① TanStack Start 의 "정규화 42배"는 쓰면 안 된다.** 이번 조사 최대 발견이다. `@tanstack/react-start` 가 304K → 76.5M 로 후보 중 압도적 1위였는데, 추이가 2026-03(2.64M) → 04(15.44M) → 05(49.94M)로 **계단식**이다. 반증 셋: 같은 계단이 `@tanstack/react-router`·`start-server-core` 에 **동시에** 찍히고(조직 전체 현상), **무관한** `@cloudflare/vite-plugin` 도 같은 4월에 2.26M → 47.64M 로 뛰었다가 7월에 19.2M 로 **후퇴**했으며, 우리가 쓰는 `@tanstack/react-query` 조차 같은 창에서 51M → 267M 로 뛴다. **정직한 결론**: Start 는 실제로도 조직 평균보다 가파르게 크는 중이지만(12월 대비 Router 18x vs react-query 5.2x), **"Next.js 다운로드의 36%" 류 헤드라인은 허구다.** 방향만 신뢰하고 배수는 버릴 것.

**② OpenAuth — 죽은 프로젝트에 붙은 가짜 5.04배.** 정규화 5.04 로 상위권이었으나 추이가 **급등 후 붕괴**다(26-03 9.15M, 04 10.63M → 05 2.15M). 레포는 이관 후 **마지막 푸시 2025-07-18**, npm 최신 **0.4.3(2025-03-04)** 로 1년 넘게 정지 상태다. "2026 오픈소스 auth 비교" 글들이 여전히 넣고 있는데, 넣으면 안 된다.

## 오늘의 학습 추천

### Cache Components — `'use cache'` 의 캐시 키와 경계 규칙

**왜 지금.** 셋이 겹친다.

① **우리는 Next 16.3 을 쓰면서 이 플래그를 안 켰다.** 프레임워크의 간판 기능을 판단 보류 상태로 두고 있는 건데, 켤지 말지를 정하려면 **캐시 키가 무엇으로 만들어지고 경계 안에서 무엇이 금지되는지**를 알아야 한다. 이건 "언젠가 볼 것"이 아니라 **버전을 올릴 때마다 미뤄지는 결정**이다.

② **이 플래그는 캐싱만 바꾸지 않는다.** 8/13 회차의 `<Activity>` — Next 16 이 클라이언트 내비게이션에서 이전 라우트를 언마운트하지 않고 hidden 으로 보존하는 동작 — 이 **`cacheComponents: true` 조건부**였다. 즉 하나를 켜면 라우팅 생명주기·state 보존·Effect 재실행까지 함께 바뀐다. 이걸 모르고 켜면 "왜 이 컴포넌트 state 가 안 초기화되지"를 디버깅하며 배우게 된다.

③ **오늘 개념 ①(AsyncLocalStorage)과 정확히 한 몸이다.** `'use cache'` 가 `cookies()`·`headers()` 를 금지하는 이유가 바로 그것들이 **요청 스코프 ALS 에서 읽는 값**이기 때문이고, 오늘 나온 Next 크래시(#97255)도 `dev` + Cache Components 조합에서 ALS 인스턴스가 갈라져 난 것이다. **캐시 경계란 결국 "요청 컨텍스트가 안 흐르는 구역"을 코드에 그은 선**이다 — 두 개념을 같이 보면 하나가 다른 하나의 이유가 된다.

**시작점 (이 순서로)**

1. [`use cache` API 레퍼런스](https://nextjs.org/docs/app/api-reference/directives/use-cache) 의 **"Cache keys" 절과 "Constraints" 절만** — 20분. 특히 *"바깥 스코프 변수가 자동 캡처돼 캐시 키가 된다"* 한 줄을 놓치지 말 것. 여기가 사고가 나는 자리다.
2. [`cacheLife`](https://nextjs.org/docs/app/api-reference/functions/cacheLife) 와 [`cacheTag`](https://nextjs.org/docs/app/api-reference/functions/cacheTag) — 수명과 무효화. **중첩 규칙**(짧은 수명을 명시적 `cacheLife` 없는 캐시 안에 넣으면 빌드 실패)까지.
3. [Node `AsyncLocalStorage` 문서](https://nodejs.org/api/async_context.html) 의 앞부분 — 왜 `cookies()` 가 프롭 없이 흐르고, 왜 캐시 경계 안에서는 못 흐르는지.
4. **실습**: 개인 프로젝트나 스크래치 앱에 `cacheComponents: true` 를 켜고, **요청과 무관한 느린 조회 하나**를 `'use cache'` 로 감싼다. 그다음 **일부러 두 가지를 해 본다** — (a) 그 함수 안에서 `headers()` 를 읽어 `next-request-in-use-cache` 에러를 직접 본다, (b) 바깥 변수 하나를 클로저로 참조하고 `NEXT_PRIVATE_DEBUG_CACHE=1` 로 **캐시 엔트리가 값마다 갈라지는지** 로그로 확인한다. 문서를 읽는 것과 이 둘을 눈으로 보는 것은 다르다.

**셀프체크**
