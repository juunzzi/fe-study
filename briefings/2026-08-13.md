# FE/AI 브리핑 — 2026-08-13 (목)

## TL;DR

- **코어 스택 stable 릴리스는 0건.** 움직인 건 Next.js canary뿐인데, 그 canary가 잡은 버그가 중요하다 — 16.3.0 stable에는 **prefetch 무한 루프**와 **revalidate 후 stale 데이터**가 아직 들어 있다. 16.3 업그레이드는 16.3.1 stable을 기다리는 게 안전하다.
- **Agent Plugins 1.0이 GitHub Copilot에서 GA(8/12).** `SKILL.md` + `mcp.json` 패키징이 특정 벤더 포맷이 아니라 **다자 공동 표준**으로 굳는 중이다. juunzzi-bot의 `skills/` 구조가 그대로 이 스펙 모양이다.
- **Biome 2.5.8이 `useReactCompiler` 규칙을 넣었다**(8/11). 어제 브리핑의 React Compiler bail-out 문제를 린터로 드러내는 경로가 하나 더 생겼다.

- **오늘의 학습**: TanStack Query 렌더 최적화 내부 — structural sharing과 tracked props. 매일 쓰는데 왜 리렌더가 안 나는지 설명 못 하면 성능 문제를 만났을 때 손댈 곳을 못 찾는다.

## 스택 업데이트

### Next.js — stable 16.3.0 유지, canary가 16.3의 버그를 줍는 중

우리 앱은 **16.2.10**, stable 최신은 **16.3.0**(8/3, 이미 다룸). `16.3.1`은 아직 미출시이고 canary만 굴러간다. 그런데 8/11~8/12 canary 네 개(`16.3.1-canary.12~15`)의 내용이 곧 **16.3.0의 알려진 결함 목록**이다.

- **prefetch 무한 루프** — optimistic routing이 prefetch를 반복하던 버그 ([canary.12](https://github.com/vercel/next.js/releases/tag/v16.3.1-canary.12)). 16.3 Instant Navigations 후속 안정화 성격이다.
- **revalidate 했는데 네비게이션 후 stale 데이터가 남던 버그** ([#95439](https://github.com/vercel/next.js/pull/95439), canary.14)
- `headers()`가 요청의 실시간 뷰로 복원 ([#97166](https://github.com/vercel/next.js/pull/97166)), `'use cache'` 파일에서 리터럴 export 허용 ([#97181](https://github.com/vercel/next.js/pull/97181))
- Turbopack: layout에서 평가된 dynamic import의 HMR 수정([#97213](https://github.com/vercel/next.js/pull/97213)), 청킹 휴리스틱에 **cluster 개념 도입**([#95157](https://github.com/vercel/next.js/pull/95157)), 캐시 stale 버전 보존 축소 + TTL([#96941](https://github.com/vercel/next.js/pull/96941))

**우리 영향**: breaking change는 없다. 16.2.10 → 16.3.0 업그레이드를 검토 중이라면 **16.3.1 stable까지 미루는 쪽**을 권한다 — 위 두 버그가 정확히 Instant Navigations를 켰을 때 밟는 지점이다.

### Biome 2.5.8 — `useReactCompiler` 규칙 추가 (8/11)

nursery 규칙으로 **React Compiler의 lint 모드 진단을 Biome이 노출**한다. 어제 브리핑에서 "컴파일러가 bail out했다는 걸 알려주는 유일한 신호가 `eslint-plugin-react-hooks`의 컴파일러 룰"이라고 썼는데, 경로가 하나 더 생긴 셈이다. Next.js 16이 `next lint`를 제거해 린터가 자유 선택 슬롯이 된 것과 맞물린다.
([릴리스](https://github.com/biomejs/biome/releases/tag/%40biomejs%2Fbiome%402.5.8))

### TanStack Query — React는 변화 없음. **"v6가 온다"는 오해 주의**

우리 `^5.99.2`, npm 최신 `5.101.4`(7/21) — 범위 안이라 `pnpm up`이면 자동으로 따라간다. 8/12에 `@tanstack/solid-query@6.0.0-rc.0`이 나왔지만 **이건 Solid 어댑터 전용**이고, 그 v6도 `query-core` **v5**에 의존한다. 어댑터별로 메이저가 따로 도는 구조라 **코어/React 어댑터의 v6 로드맵은 공식적으로 확인되지 않는다**. 검색하면 `migrate-from-v5-to-v6` 문서가 잡히는데 그건 Svelte 어댑터의 runes 전환 문서다 — 여기 속으면 안 된다.
([releases](https://github.com/TanStack/query/releases))

## AI 소식

### Agent Plugins 1.0이 Copilot에서 GA — 이번 주의 진짜 사건

모델이 아니라 **표준**이 이번 창의 헤드라인이다. 8/6 스펙 1.0.0 발표(AWS·Anysphere·GitHub·Microsoft·OpenAI·Vercel + Google 참여)에 이어 **8/12 GitHub Copilot 전 제품에서 GA**됐다 — VS Code, Copilot CLI, Copilot SDK, 전 플랜.

구성은 최소한이다: 루트 `plugin.json`(`$schema`·`name` 필수) + `skills/*/SKILL.md` + 선택적 `mcp.json`. **명시적 범위 밖**인 것이 더 중요하다 — 설치·권한·보안·샌드박싱, 그리고 commands·hooks·agents·rules는 "v1 포터블 계약에 넣기엔 너무 클라이언트 특화"라 빠졌다. 적합성 요건에 failure isolation이 있어 미지원 구성요소가 있어도 나머지는 로드돼야 한다.

- 스펙 상태는 **"1.0.0 Working Draft"** — 최종 확정이 아니다. ([스펙](https://agent-plugins.org/specification))
- "OpenAI가 만든 표준"으로 쓴 기사가 많은데 **틀렸다**. 1차 출처는 다자 공동 + 독립 거버넌스로 기술한다.
- VS Code는 Agent Plugins 1.0 / Copilot 포맷 / **Claude 포맷(`.claude-plugin/plugin.json`)** / 레거시를 병행 지원한다. ([문서](https://code.visualstudio.com/docs/agent-customization/agent-plugins))
- ([Vercel 발표](https://vercel.com/blog/introducing-agent-plugins) · [GitHub changelog](https://github.blog/changelog/2026-08-12-agent-plugins-1-0-in-vs-code-copilot-cli-and-the-copilot-app/))

**우리 연결점**: juunzzi-bot의 `skills/<도구>/SKILL.md` 구조가 이미 이 스펙과 같은 모양이다. registry 배열로 노출 경계를 코드에서 통제하는 부분이 스펙의 범위 밖(권한·보안)에 해당한다 — 표준이 안 정해준 자리를 우리가 어떻게 메웠는지가 그대로 드러난다.

## 지금 알아둘 개념

### ① TanStack Query는 왜 리렌더가 안 나는가 — structural sharing + tracked props

**무엇인가.** 우리가 매일 쓰는 `useQuery`가 리렌더를 억제하는 장치는 두 겹이다.

**첫째, structural sharing.** 서버가 매번 새 JSON을 주더라도, Query가 이전 데이터와 새 데이터를 **깊이 비교해 바뀐 부분만 교체하고 나머지는 이전 참조를 그대로 유지**한다. 소스(`replaceEqualDeep`)의 마지막 줄이 전부다 — 전부 같으면 이전 참조 `a`를 그대로 돌려준다.

```ts
return aSize === bSize && equalItems === aSize ? a : copy
```

그래서 `data`를 의존성으로 쓰는 `useMemo`·`useEffect`·`memo` 자식이 재실행되지 않는다. **단, JSON 호환 데이터일 때만이다** — `isPlainArray`도 `isPlainObject`도 아니면 그냥 새 값을 넘긴다(Class 인스턴스·Map·Date는 공유 대상 밖). 재귀 깊이 500 초과도 마찬가지. 끄려면 `structuralSharing: false`.

**둘째, tracked props.** `useQuery`는 내부적으로 `QueryObserver`를 만들어 `useSyncExternalStore`로 구독하고, 반환 직전 `observer.trackResult(result)`를 통과시킨다. 이게 결과를 **Proxy로 감싸서 컴포넌트가 실제로 접근한 키만 기록**한다. 알림 판정은 그 `#trackedProps` 기준이다.

즉 **`isFetching`을 구조분해하지 않았다면 백그라운드 refetch가 리렌더를 만들지 않는다.** 반대로 로깅하겠다고 무심코 전부 구조분해하면 이 최적화가 통째로 사라진다. `notifyOnChangeProps: 'all'`은 이걸 명시적으로 끄는 옵션이다.

한 가지 더: **훅이 반환하는 최상위 객체는 참조 안정적이지 않다**(매 렌더 새 참조). 안정적인 건 `data` 내부다 — 이걸 혼동하면 "structural sharing이 왜 안 먹지"라는 잘못된 질문에 빠진다.

**왜 지금.** ① 우리는 `^5.99.2`로 5.101.x를 자동 추적 중이고 이 동작 위에 화면 전체가 서 있다. ② `staleTime`/`gcTime`을 만지는 건 다들 하는데, **리렌더가 왜 나는지/안 나는지**는 위 두 겹을 모르면 설명이 안 된다 — 그러면 성능 문제를 만났을 때 손댈 곳을 못 찾고 `useMemo`를 뿌리게 된다. ③ 어제 다룬 React Compiler와 정면으로 맞물린다: 컴파일러가 자동 메모이제이션을 넣는 세계에서 **참조 안정성을 누가 보장하느냐**가 바로 이 지점이다.

**실코드 연결.** 우리 앱의 리스트 화면에서 ① `useQuery` 결과를 구조분해하는 자리에 `isFetching`·`isPending`이 불필요하게 끼어 있는지 ② `select` 옵션이 매 렌더 새 함수를 만들어 structural sharing 이득을 깎고 있는지(`select`는 참조가 바뀌면 재실행된다) ③ `queryFn`이 Date나 클래스 인스턴스로 변환해 반환하는 자리가 있는지 — 있다면 structural sharing이 그 쿼리에는 아예 안 걸린다.

### ② `<Activity>` — 언마운트 대신 "숨기기", 그리고 그 대가

**무엇인가.** `<Activity mode="hidden">`은 children을 `display: none`으로 숨기고 **Effect를 언마운트**하되 **state와 DOM은 보존**한다(useState 값, textarea 입력, 스크롤 위치, 비디오 재생 위치). 업데이트는 낮은 우선순위로 지연된다. `mode="visible"`이 되면 Effect가 다시 마운트된다. 조건부 렌더(`{isVisible && <C/>}`)와의 차이가 핵심이다 — 후자는 언마운트하며 state를 파괴한다.

**여기가 실전 함정이다**: state는 남는데 Effect는 정리·재실행된다. **비대칭이다.** "마운트 시 1회"라고 믿고 쓴 Effect가 다시 돌고, "이건 초기화됐겠지" 하고 믿은 state는 안 초기화된다.

**왜 지금.** ① `<Activity>`는 실험이 아니다 — **React 19.2 정식 API**다(우리는 19.2.7). ② **Next.js 16이 `cacheComponents: true`일 때 클라이언트 내비게이션에서 이전 라우트를 언마운트하지 않고 Activity hidden으로 보존한다.** 즉 Cache Components를 켜는 순간 이 동작이 앱 전체에 걸린다 — 기본 동작이 아니라 플래그 조건부라는 게 중요하다. ③ 공식 마이그레이션 문서가 경고하는 함정 세 가지가 그대로 QA 체크리스트다:
- **드롭다운·팝오버**: 뒤로 가면 열린 채로 남는다 → `useLayoutEffect` cleanup에서 닫아라
- **다이얼로그**: state가 보존돼 "입력 포커스" 같은 effect가 재발화하지 않는다 → 다이얼로그 상태를 URL에서 파생시켜라
- **제출한 폼**: 입력값과 `useActionState` 결과(성공/에러 메시지)가 남는다 → 제출 핸들러에서 리셋

**곁다리 — Fragment refs는 아직 canary다.** 8/11~12 React canary 커밋이 `<Fragment ref>`(FragmentInstance) 마무리에 집중하고 있다([#37166](https://github.com/facebook/react/pull/37166), [#37165](https://github.com/facebook/react/pull/37165)). 래퍼 `<div>` 없이 자식 그룹에 `addEventListener`·`focus()`·`observeUsing(IntersectionObserver)`를 걸 수 있게 하는 API다. `<Activity>`와 같은 React Labs 글에서 함께 소개돼 상태가 같다고 착각하기 쉬운데 **지금은 갈렸다** — Activity는 stable, Fragment refs는 canary 전용이다.

**셀프체크**
① `mode="hidden"`으로 숨겨진 트리에서 `useEffect`의 cleanup은 언제 실행되는가? state는 어떻게 되는가?
② Cache Components를 켠 앱에서 "뒤로 갔다 오면 모달이 열려 있다"는 버그가 났다. 원인과 고치는 자리는?
③ 조건부 렌더 대신 `<Activity>`를 쓰면 안 되는 경우는 언제인가? (힌트: 보존되면 안 되는 state)

- [`<Activity>` 레퍼런스](https://react.dev/reference/react/Activity) · [React 19.2 릴리스](https://react.dev/blog/2025/10/01/react-19-2)

## 떠오르는 스택 레이더

### ① Rust 툴체인의 통합 — Oxc / Rolldown / Vite 8 (주류 진입 완료)

**뭐가 다른가.** 지금 우리 빌드는 "여러 도구가 같은 파일을 각자 다시 파싱"하는 구조다 — SWC로 트랜스폼, ESLint가 다시 AST 생성, Prettier가 또 파싱, `tsc`가 또. Oxc는 **파서 하나(Rust)를 만들고 린터(oxlint)·포매터·트랜스포머·번들러(Rolldown)가 그 AST를 공유**한다. Vite 8은 esbuild(dev) + Rollup(prod) 이중 구조를 버리고 Rolldown 단일 파이프라인으로 갔다 — **dev/prod 산출물 불일치라는 고질병이 아키텍처 차원에서 사라진다.**

**성숙도·채택 신호.** Vite 8 정식은 2026-03-12. 주간 다운로드는 `vite` 1.64억 / `rolldown` 8,867만 / `oxlint` 1,486만이고, oxlint 월간은 2025-08 173만 → 2026-07 5,259만으로 **약 30배**다. ESLint(주간 1.56억) 대비 아직 9.5% 규모지만 기울기가 다르다. GitHub 스타는 oxc 22.3k / rolldown 13.9k. 실측 빌드 개선으로 Linear 46s→6s, Ramp −57%, beehiiv −64%가 공개돼 있다. **2026-06-04 Cloudflare가 VoidZero를 인수**했고 Vite/Vitest/Rolldown/Oxc는 오픈소스 유지 + 100만 달러 커뮤니티 펀드 조건이다.

**지금 알아둘 이유 한 줄.** Next.js 16이 `next lint`를 제거하고 빌드 중 ESLint 실행도 없앴기 때문에 **린터는 이제 자유 선택 슬롯**이다 — Vite를 안 써도 oxlint만 갈아끼우는 건 오늘 바로 가능한 저위험 실험이다.

([Vite 8 발표](https://main.vite.dev/blog/announcing-vite8) · [oxc.rs](https://oxc.rs/) · [Cloudflare 인수](https://www.cloudflare.com/press/press-releases/2026/cloudflare-acquires-voidzero-to-build-the-future-of-the-ai-native-web/) · [Next 16 업그레이드 문서](https://nextjs.org/docs/app/guides/upgrading/version-16))

### ② WebMCP (`document.modelContext`) — 에이전트가 소비하는 UI (실험, 과대평가 금지)

**뭐가 다른가.** "AI가 우리 서비스를 쓰게 한다"의 기존 답은 브라우저 자동화(픽셀·DOM 조작)거나 별도 백엔드 MCP 서버였다. WebMCP는 **이미 로그인·세션·권한을 들고 있는 페이지 자신이** `document.modelContext.registerTool({ name, description, inputSchema, execute })`로 자기 기능을 도구로 등록하고 브라우저 에이전트가 그걸 호출한다. React 컴포넌트가 사람용 렌더 트리 외에 **에이전트용 도구 표면**을 하나 더 갖는 모델 — 별도 서버도, 인증 재구현도 없다.

**성숙도.** 냉정하게 봐야 한다. Chrome Status **"Proposed"**, 스펙 성숙도는 **W3C 정식 트랙이 아니라 Community Group 인큐베이션**이다. dev trial Chrome 146, 오리진 트라이얼 Chrome 149. **Firefox·Safari는 둘 다 "No signal"**. 레포 스타 2,988(최근 커밋 8/12로 활발). 실사용은 사실상 0 — 주요 에이전트 중 WebMCP 도구를 실제로 호출하는 곳이 없다. API 위치가 `navigator.modelContext` → `document.modelContext`로 옮겨간 것(2026-07)도 아직 흔들린다는 신호다.

**지금 알아둘 이유 한 줄.** 도입할 물건이 아니다. 다만 방향이 확정되면 "프론트는 UI만 만든다"는 전제가 깨지고 **동작을 스키마화 가능한 단위로 노출할 수 있는가**가 새 컴포넌트 설계 축이 된다 — 트라이얼 기간 동안 개념만 잡아두면 충분하다.

## 오늘의 학습 추천

### TanStack Query 렌더 최적화 내부 — structural sharing과 tracked props

**왜 지금.** 세 가지가 겹친다. ① 우리 앱의 데이터 계층 전체가 이 동작 위에 서 있는데, `staleTime`·`gcTime`은 다들 만지면서 **리렌더가 왜 나는지/안 나는지**는 설명하기 어렵다 — 그 상태로 성능 문제를 만나면 손댈 곳을 못 찾고 `useMemo`를 뿌리게 된다. ② 어제 다룬 **React Compiler와 정면으로 맞물린다.** 컴파일러가 자동 메모이제이션을 넣는 세계에서 캐시 무효화의 근거는 **참조 동일성**이고, 그 참조를 서버 데이터 쪽에서 만들어 주는 게 정확히 structural sharing이다. 두 층이 각각 무엇을 보장하는지 구분 못 하면 "컴파일러가 켜져 있는데 왜 리렌더가 나지"라는 질문에 답할 수 없다. ③ v6 로드맵이 없어서 v5 내부 지식의 수명이 길다 — 지금 판 것이 오래 간다.

**시작점 (이 순서로)**
1. [Render Optimizations](https://tanstack.com/query/latest/docs/framework/react/guides/render-optimizations) — 문서는 짧다. 10분.
2. [`replaceEqualDeep` 소스](https://github.com/TanStack/query/blob/main/packages/query-core/src/utils.ts) — 함수 하나다. **어떤 타입에서 bail하는지** 를 눈으로 확인하는 게 핵심.
3. [`useBaseQuery`](https://github.com/TanStack/query/blob/main/packages/react-query/src/useBaseQuery.ts) → [`queryObserver.ts`의 `trackResult`](https://github.com/TanStack/query/blob/main/packages/query-core/src/queryObserver.ts) — Proxy로 접근 프로퍼티를 기록하는 자리.
4. 실측: 우리 앱 리스트 화면에서 `useQuery` 구조분해 목록을 하나씩 빼 보며 백그라운드 refetch 시 리렌더 횟수를 센다. Devtools보다 `console.count`가 빠르다.

**셀프체크**
① `staleTime: Infinity`인데도 캐시가 지워지는 상황은? (`gcTime`과의 관계로)
② `queryFn`이 클래스 인스턴스나 `Date`를 반환하면 structural sharing에 무슨 일이 생기는가?
③ `isFetching`을 구조분해했을 때와 안 했을 때, 백그라운드 refetch 한 번에 리렌더는 각각 몇 번인가? 그 차이를 만드는 코드 한 줄은 어디에 있는가?
④ React Compiler의 자동 메모이제이션과 structural sharing은 **각각 무엇을 보장하는가.** 하나만 있으면 못 막는 리렌더는 어떤 모양인가?
