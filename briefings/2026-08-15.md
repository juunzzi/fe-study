# 2026-08-15 (토) FE/AI 브리핑

## TL;DR

- **Next.js 16.3.1 stable (8/13)** — 지난 브리핑에서 "canary가 줍는 중"이라던 Instant Navigations 버그가 실제로 백포트됐다. 순수 패치, breaking 없음 → **16.3.0 쓰는 곳은 올릴 이유가 생겼다.**
- **TypeScript는 이미 7.x가 npm `latest`다** — 그리고 그 개발선은 `microsoft/TypeScript` 가 아니라 **`microsoft/typescript-go`** 다. 우리가 고정한 6.0.3은 6.x 최종본(4/16)이고 이후 릴리스가 없다. 이건 "이번 주 뉴스"가 아니라 **누적 부채**다.
- **React canary가 `enableParallelTransitions` 를 켰다(8/14)** — 2월에 "실수로 켰다"며 껐던 플래그를 이번엔 의도적으로 되돌렸다. 19.2.8엔 영향 없지만 19.3 관찰 대상.
- **Safari TP 250 (8/13)** 에 `using` / `await using`(Explicit Resource Management)과 스트리밍 업로드(`duplex`)가 들어왔다 — 오늘의 학습 주제로 골랐다.
- **DeepSeek 이 하네스를 직접 소유하러 나섰다** — `deepseek-harness` 가 공개 이틀 만에 95k 스타. 모델 회사가 실행 환경까지 가져가는 흐름이 이 창의 가장 큰 구조 변화다.

## 스택 업데이트

### Next.js 16.3.0 → **16.3.1 stable** (2026-08-13)

핵심은 **optimistic routing 의 prefetch 무한 루프 수정**([#97325](https://github.com/vercel/next.js/pull/97325))과 Nav Inspector 반복 캡처 루프([#97326](https://github.com/vercel/next.js/pull/97326))다. 8/13 브리핑에서 "16.3.1 stable 까지 미루라"고 썼던 그 두 버그가 바로 이거고, 이제 나왔다.

같이 들어온 것:

- **`'use cache'` 정합성 묶음** — 태그 리밸리데이션 시 완료 항목을 재사용([#97314](https://github.com/vercel/next.js/pull/97314)), `unstable_cache` 캐시 아이템 이름 인코딩([#97313](https://github.com/vercel/next.js/pull/97313)), `headers()` 의 live view 복원([#97311](https://github.com/vercel/next.js/pull/97311)).
- **Turbopack** — 레이아웃에서 평가된 dynamic import 의 HMR 깨짐([#97317](https://github.com/vercel/next.js/pull/97317)), 공유 런타임 청크에서 async-module 런타임 stripping([#96653](https://github.com/vercel/next.js/pull/96653)), Pages Router SSR 에서 styled-jsx 스타일 누락([#97302](https://github.com/vercel/next.js/pull/97302)).

**우리 영향**: breaking change **없음**. 16.3.0 → 16.3.1 은 전부 fix/backport 다. prefetch 루프는 불필요한 네트워크 요청을 만드는 종류라 체감·비용 양쪽에 걸린다. **올려도 되는 정도가 아니라 올리는 게 맞다.**
canary 는 이미 `.19`(8/14)까지 갔고 napi-rs v2→v3 마이그레이션([#95412](https://github.com/vercel/next.js/pull/95412)), 프리페치 응답 포맷 통일(`NavigationFlightResponse`), React `eb8feb71-20260814` 상향이 올라와 있다 — 아직 stable 아니니 지금 볼 건 아니다.

([릴리스](https://github.com/vercel/next.js/releases/tag/v16.3.1))

### TypeScript — **6.0.3 은 6.x 의 마지막이다** (이번 주 뉴스가 아니라 지형 정정)

조사 중 함정 하나를 실제로 밟아서 그대로 남긴다. `github.com/microsoft/TypeScript/releases` 만 보면 **6.0.3 (2026-04-16) 이 최신으로 보인다.** 실제로는 npm `latest` 가 **7.0.2 (2026-07-08)** 이고, TS 7.x 는 **Go 네이티브 포트인 [`microsoft/typescript-go`](https://github.com/microsoft/typescript-go/releases)** 에서 개발된다. 구 레포는 4개월째 릴리스가 없다.

이번 창(8/12~15) 안에 정식 릴리스는 없고 나이틀리 2개(`7.1.0-dev.20260813.1` 등)뿐이다. typescript-go 머지 27건도 전부 버그픽스·포팅·LSP 안정화이고 언어 기능 변경은 없다. 눈에 띄는 건 체커 병렬화(`balanced import affinity`)와 메모리 회귀 수정 정도.

**우리 영향**: 지금 당장 깨지는 건 없다. 다만 우리는 **유지보수가 끝난 라인에 고정**돼 있고, 6→7 은 컴파일러 자체를 다시 쓴 메이저라 마이그레이션은 별건으로 다뤄야 한다. 7.0 의 구체적 breaking 목록은 이번 조사 범위 밖 — **미확인**.

**당장 할 일 하나**: 릴리스 모니터링 소스를 `microsoft/TypeScript` → `microsoft/typescript-go` 로 바꾼다. 안 바꾸면 TS 7.x 소식을 영영 못 본다.

### React 19.2.8 — 정식 릴리스 없음 / canary 에서 **`enableParallelTransitions` ON** (8/14)

[#37290](https://github.com/facebook/react/pull/37290) 이 OSS·canary 기본값과 RN 포함 하드코딩 포크에서 이 플래그를 켰다. 이력이 재미있다 — 2026-02-05 [#35709](https://github.com/facebook/react/pull/35709) 에서 *"Accidentally enabled this"* 라며 껐던 것을 **이번엔 의도적으로 되돌린 것**이다. 플래그는 아직 레포에 남아 있고 www 는 GK 구동이라 미변경.

Fragment refs 도 계속 굴러간다 — 8/13 브리핑의 #37166/#37165 **이후** 2건이 더 머지됐다([#37169](https://github.com/facebook/react/pull/37169) once 리스너를 자식이 아니라 fragment 스코프로, [#37168](https://github.com/facebook/react/pull/37168) HostText 자식의 삭제 이펙트).

**우리 영향**: **없다.** 전부 19.3.0-canary 한정이고 19.2.x 로 백포트되지 않았다. 다만 parallel transitions 는 **동시 실행된 transition 의 스케줄링 의미를 바꾸는 성격**이라 `startTransition` 을 적극적으로 쓰는 코드가 19.3 에서 동작이 달라질 후보다(구체 semantics 는 PR 본문에 설명이 없어 **미확인** — 아래 "지금 알아둘 개념 ②"에서 현재 모델만 정리했다).

### TanStack Query — 우리와 무관 / **v6 는 여전히 solid 쪽 얘기다**

`@tanstack/react-query` 는 5.101.4(7/21) 에서 3.5주째 정지. 이 창의 유일한 릴리스는 **`@tanstack/solid-query@6.0.0-rc.0`(8/12)** 이고 내용은 Solid v2 RC 대응 + vite 플러그인 리네임이다. 8/13 브리핑에서 짚은 "v6 온다는 오해"를 한 번 더 확인해 준다 — **react-query 는 5.x 다.** 창 안 react-query 머지는 문서 PR 1건뿐.

곁다리로 tanstack.com 에 **[Inside a TanStack Router Navigation](https://tanstack.com/blog)** (8/14, Florian Pellet) 이 올라왔다. Query 가 아니라 Router 해설이다.

`tc39/proposals` 는 **2026-07-25 이후 커밋 0건**(`since` 두 번 교차 확인). 8월은 정기 미팅이 없는 달로 보인다(agendas 레포에 2026/08 항목 미확인 — 공식 취소 공지는 확인 못 함). 직전 stage 이동은 전부 7월 미팅분이라 이번 창 소식이 아니다.

## 지금 알아둘 개념

### ① Explicit Resource Management — `using` / `await using`, 그리고 "해제"가 문법이 된다는 것

**무엇인가.** `try/finally` 로 손수 쓰던 자원 해제를 **선언 문법과 프로토콜**로 올린 것이다. 객체가 `Symbol.dispose`(동기) 또는 `Symbol.asyncDispose`(비동기) 메서드를 갖고 있으면, `using`/`await using` 으로 선언한 바인딩은 **스코프를 벗어날 때 자동으로 그 메서드가 불린다.** 순서는 선언의 **역순**이고, 예외로 빠져나가도 불린다.

```ts
{
  using db = openDatabase();       // 블록 끝에서 db[Symbol.dispose]()
  await using conn = await connect(); // 블록 끝에서 await conn[Symbol.asyncDispose]()
}                                   // conn → db 순으로 해제
```

같이 딸려오는 게 **`DisposableStack` / `AsyncDisposableStack`** 이다. 여러 자원을 한 스택에 모아 `defer()`·`adopt()`·`use()` 로 등록하고, 스택 하나가 해제되면 전부 역순으로 정리된다. **생성 도중 중간에 실패했을 때 이미 만든 것만 정확히 되돌리는 문제**(`move()`)가 여기서 해결된다 — 손으로 짜면 거의 항상 틀리는 자리다.

**왜 지금.** 세 갈래가 이번 주에 겹쳤다. ① **Safari TP 250(8/13) 이 이걸 구현했다** — 마지막 주요 엔진이 들어오면서 "TS 로 트랜스파일해서 쓰는 문법"에서 "브라우저가 실행하는 문법"으로 성격이 바뀌는 중이다. ② TypeScript 는 이미 5.2부터 지원하고 Node 도 24부터 플래그 없이 돈다 — 즉 **언어·런타임·브라우저 셋이 이제 같은 자리에 서 있다.** ③ 더 중요한 이유: 요즘 우리가 다루는 자원이 죄다 이 모양이다. MCP 커넥션, 장수명 SSE/WebSocket 스트림, SQLite 핸들, `AbortController`, 파일 핸들. **위 AI 소식의 "MCP v2 가 스트림을 무한 재오픈하던 버그"가 정확히 이 범주의 실패다** — 누가 언제 닫는지가 코드에 안 적혀 있으면 새는 건 시간문제다.

**실코드 연결 (juunzzi-bot).** 잘 맞는 자리가 여럿이다. ① `src/mcp/` 의 커넥션 — dejavu MCP 가 npx 폴백까지 타는 경로에서 실패 시 정리가 `finally` 에 흩어져 있다면 `AsyncDisposableStack` 한 개로 모을 수 있다. ② SQLite 잡 큐(`var/juunzzi-bot.db`) 의 statement/트랜잭션 — 트랜잭션 안에서 예외가 나는 경로마다 rollback 을 손으로 부르고 있다면 `using` 이 그걸 구조적으로 없앤다. ③ 슬랙 스트리밍 응답(`chat.startStream`) — 시작한 스트림을 반드시 닫아야 하는데, 에러 경로가 늘 때마다 닫는 자리가 하나씩 빠지는 전형적인 모양이다. ④ 8/14 DNS 장애 때 37번 시도가 쌓인 사건도 결국 "붙들린 자원과 그 해제"를 누가 소유하는가의 문제다.

**셀프체크**
① `using x = null` 은 던지는가 안 던지는가? `undefined` 는? (이걸 알아야 옵셔널 자원을 다룰 수 있다)
② `using` 이 선언된 스코프에서 예외가 나고, **dispose 가 또 예외를 던지면** 어느 예외가 호출자에게 가는가? (`SuppressedError` 를 찾아볼 것)
③ 자원을 **만든 함수가 아니라 호출자가 소유해야 할 때** `DisposableStack.move()` 는 무엇을 보장하는가? 그게 없으면 어떤 버그가 나는가?
④ `await using` 은 `for await` 루프 안에서 매 이터레이션마다 해제되는가, 루프 종료 시 한 번인가?

([TC39 제안](https://github.com/tc39/proposal-explicit-resource-management) · [TypeScript 5.2 릴리스 노트](https://devblogs.microsoft.com/typescript/announcing-typescript-5-2/) · [Safari TP 250](https://webkit.org/blog/18191/release-notes-for-safari-technology-preview-250/))

### ② Transition 은 "여러 개"가 아니라 "하나의 차선"이었다 — parallel transitions 가 바꾸려는 것

**무엇인가.** `startTransition` 은 흔히 "이 업데이트를 낮은 우선순위로 표시" 정도로 이해된다. 실제 스케줄러 모델은 그보다 구체적이다 — React 는 업데이트를 **lane** 이라는 비트 단위 차선에 넣어 스케줄하고, transition 업데이트들은 **서로 얽혀(entangle) 같은 차선으로 묶이는** 성질이 있다. 그래서 서로 무관한 두 transition 이 동시에 진행 중이면, **느린 쪽이 끝날 때까지 빠른 쪽 결과도 커밋되지 않는** 상황이 생긴다. 하나의 일관된 화면 상태를 보장하려는 설계의 대가다.

`enableParallelTransitions` 는 이 얽힘을 풀어 **독립적인 transition 이 각자 커밋되게** 하려는 방향의 플래그로 읽힌다. 다만 **정확한 semantics 는 PR 본문에 설명이 없어 미확인**이다 — 여기서 확실하게 말할 수 있는 건 "현재 모델이 저렇게 생겼다"까지고, 19.3 릴리스 노트를 기다려야 한다. (이 브리핑에서 확인한 사실은 딱 둘: 2월에 실수로 켰다가 껐고([#35709](https://github.com/facebook/react/pull/35709)), 8/14 에 의도적으로 켰다([#37290](https://github.com/facebook/react/pull/37290)).)

**왜 지금.** ① 우리는 19.2.8 이라 **오늘 영향은 0** 이다. 그래서 지금이 **부담 없이 모델만 이해해 둘 타이밍**이다 — 19.3 이 나온 뒤에 "왜 갑자기 순서가 달라졌지"를 디버깅하며 배우면 늦다. ② 우리 앱이 Instant Navigations 계열 기능을 검토 중이라면 이건 남 얘기가 아니다. **라우터 내비게이션이 내부적으로 transition 이고**, 위 Next 16.3.1 이 고친 optimistic routing 버그도 이 층에서 벌어진 일이다. ③ 8/12~13 에 다룬 React Compiler·structural sharing 이 "무엇을 다시 렌더할까"의 문제였다면, 이건 **"언제 커밋할까"** 의 문제다. 렌더 최적화의 나머지 절반이다.

**실코드 연결.** 우리 앱에서 확인해 볼 것 세 가지: ① `startTransition` 안에서 라우터 내비게이션과 별개 상태 업데이트를 **같이** 부르는 자리가 있는가(그렇다면 지금은 함께 묶여 커밋된다). ② `useTransition` 의 `isPending` 으로 스피너를 띄우는 화면에서, 그 스피너가 **관련 없는 다른 transition 때문에** 오래 떠 있던 적이 있는가. ③ Suspense 경계(8/10 에 다뤘다)와의 관계 — transition 중에는 이미 보이던 콘텐츠가 fallback 으로 대체되지 않는다는 규칙이 어디까지 유효한가.

**셀프체크**
① transition 업데이트와 일반 업데이트가 같은 렌더 사이클에 들어오면 React 는 무엇을 먼저 커밋하는가?
② `useDeferredValue` 와 `startTransition` 은 같은 lane 을 쓰는가? 둘 중 하나만 있어도 되는 상황은?
③ transition 중 사용자가 입력을 하면(= 더 높은 우선순위 업데이트) 진행 중이던 렌더는 버려지는가, 이어지는가? 버려진다면 그 사이 실행된 `useEffect` 는?
④ 두 transition 이 얽히면 안 되는 대표 사례를 하나 만들어 보라 — 그게 이 플래그가 겨냥한 문제다.

## 오늘의 학습 추천

### Explicit Resource Management — `using` / `await using`, 그리고 `DisposableStack`

**왜 지금.** 세 가지가 겹친다.

① **타이밍이 정확히 지금이다.** Safari TP 250(8/13)이 구현하면서 TS(5.2+)·Node(24+)·브라우저 셋이 처음으로 같은 자리에 섰다. "언젠가 되는 문법"이 아니라 **지금부터 실제로 실행되는 문법**이고, 그 말은 앞으로 남의 코드에서 `using` 을 읽게 된다는 뜻이다.

② **오늘 다룬 다른 항목들이 전부 이 문제로 수렴한다.** AI 소식의 "MCP v2 가 스트림을 무한 재오픈하던 버그", Zustand 의 "`clearStorage()` 가 진행 중인 rehydration 을 무효화 못 하던 버그" — 둘 다 **자원의 소유자와 해제 시점이 코드에 안 적혀 있어서** 생긴 실패다. 문법이 이걸 구조적으로 표현하게 해준다.

③ **개인 프로젝트에 바로 꽂을 자리가 있다.** juunzzi-bot 의 MCP 커넥션(dejavu 가 npx 폴백까지 타는 경로), SQLite 잡 큐의 트랜잭션, 슬랙 스트리밍 응답 — 셋 다 "에러 경로가 늘어날 때마다 닫는 자리가 하나씩 빠지는" 전형이다. 앞의 두 학습 추천(node:sqlite, React Compiler)과 달리 이건 **읽는 지식이 아니라 오늘 커밋으로 바뀌는 지식**이다.

**시작점 (이 순서로)**

1. [TypeScript 5.2 릴리스 노트의 해당 절](https://devblogs.microsoft.com/typescript/announcing-typescript-5-2/) — 문법·타입(`Disposable`/`AsyncDisposable`) 전체가 여기 한 페이지에 있다. 15분.
2. [TC39 proposal README](https://github.com/tc39/proposal-explicit-resource-management) — **`SuppressedError` 절과 `DisposableStack.move()` 절만** 읽으면 된다. 나머지는 1번과 겹친다. 여기가 진짜 핵심이다.
3. [MDN `Symbol.dispose`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Symbol/dispose) 로 현재 브라우저·런타임 지원 상태 확인.
4. **실습**: juunzzi-bot 에서 `try/finally` 로 자원을 닫는 자리 하나를 골라 `using` 으로 바꿔 본다. 그다음 **에러 경로를 일부러 하나 더 추가**해서, 기존 코드였다면 닫는 걸 빠뜨렸을 자리가 자동으로 닫히는지 확인한다. 이게 이 문법의 값어치를 몸으로 아는 유일한 방법이다.

**셀프체크**

① `using x = null` / `= undefined` 는 던지는가? (옵셔널 자원을 다루려면 반드시 알아야 한다)
② 본문에서 예외가 나고 **dispose 도 예외를 던지면** 호출자는 어느 예외를 받는가? `SuppressedError` 의 `error` 와 `suppressed` 는 각각 무엇인가?
③ 자원을 **만든 함수가 아니라 호출자가 소유해야 할 때** — 팩토리 함수가 중간에 실패하면 이미 만든 것만 되돌리고, 성공하면 소유권을 넘겨야 한다. `DisposableStack.move()` 가 없으면 어떤 버그가 나는가?
④ `await using` 은 `for await` 루프에서 **매 이터레이션마다** 해제되는가, 루프 종료 시 한 번인가? 스트림을 순회하는 코드에서 이 차이가 왜 치명적인가?
⑤ 내 코드에서 `using` 으로 못 바꾸는 `try/finally` 는 어떤 모양인가? (해제 시점이 스코프와 일치하지 않는 경우 — 그게 `DisposableStack` 이 필요한 자리다)
